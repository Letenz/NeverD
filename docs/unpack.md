# Unpacking packed executables

`neverd unpack` recovers the program that a packed executable rebuilds in its own address space. It runs the input as a bounded guest process, observes where the stub hands control to the code it produced, and writes that image as a new file of the same container. It does not devirtualize: functions a protector virtualized stay virtualized. Build with `NEVERD_ENABLE_CPU_EMULATION=ON`.

## Supported inputs

The container selects how a file is validated and rebuilt, the instruction set selects how a transfer is judged, and both select the guest process profile. An input outside this table is rejected by name before anything executes.

| Container (`format`) | Instruction set | Guest profile | Stub knowledge |
| --- | --- | --- | --- |
| PE32+ (`pe64`) | x86-64 | [`windows-pe64-v1`](process-emulation.md) | UPX |
| PE32+ (`pe64`) | ARM64 | [`windows-pe64-v1`](process-emulation.md) | none; observation only |

## Use

```bash
neverd unpack packed.exe -o unpacked.exe
neverd unpack packed.exe -o unpacked.exe \
  --options='{"backend":"unicorn","instruction_limit":400000000,"transfer":2}'
```

The command prints one JSON report. Exit code 0 means the image was written, 3 means the bounded run ended before an entry was accepted (`outcome` is `no_entry` and nothing is written), and 1 is an invalid input, option or setup failure. The report names the `format`, the `architecture` and the `profile` that ran. The C entry point is `neverd_unpack_json`; Python exposes `Session.unpack`. Options are the [process options](process-emulation.md) plus `transfer`. Defaults differ where a stub needs more room: 100000000 instructions, 600 seconds and 512 MiB, and `windows.defer_unmodeled` is on.

## How the entry is established

Generation zero is the image as the guest loader mapped it. An instruction whose bytes differ from that image was generated by the process. A transfer is the first execution of code newer than the code that was running; `transfers` lists each one with its RVA, `generation` and whether the stack pointer equals its value at process entry (`stack_balanced`).

1. A transfer on the entry stack is the program's entry: the stub has returned the stack it was given. `entry_source` is `transfer`.
2. A transfer on a deeper stack is a call the stub makes into the program, such as a TLS callback. It is reported, not accepted. When the identified stub names its final jump target, the image is rebuilt at that call, before any code of the program has run, and the named address is the entry. `entry_source` is `stub`.
3. `transfer` selects a listed transfer by position, for protectors that unpack in stages or call their program.

No entry is predicted from the shape of compiler startup code. A run that stops first reports `no_entry` with the process `stop_reason`.

## The rebuilt image

Sections keep their RVAs and hold the observed memory; each section has the access its pages had at the transfer. A final `.neverd` section holds a new import directory over the cells the program already calls through, so no code or data moves. `imports` lists every cell with its `origin`: `static` cells were bound by the loader from the input's own directory, `runtime` cells were stored by the stub. The image is fixed at its observed base: relocations of generated content were not observed, so the relocation directory is removed and `IMAGE_FILE_RELOCS_STRIPPED` is set. For UPX the program's own TLS directory is named again, because the packed one reaches only the stub's handler.

The original section table, import directory layout and relocation table are not reconstructed; a packer does not restore them in memory.

## Identification

`packer.kind` names a protector only from evidence in the file. UPX needs two of `upx_section_names`, `upx_pack_header` (magic, format, method and checksum) and `upx_entry_stub`. An unidentified input is still unpacked by observation.

## Limits

Executables only; DLLs are not run. Checked execution admits one instruction at a time, on the order of 10^5 per second, so a stub that needs billions of instructions exceeds any practical budget. Execution is tracked per 4 KiB page: code written into a page that is already running code of the same generation is not reported as a transfer. Code of the program that runs before the entry, such as a TLS callback that calls an unmodeled API, stops the run unless the stub declares its entry. A VMProtect loader is unpacked when each protected import call is still a six-byte site that tail-calls a resolved export. Those sites are rewritten as ordinary import calls. Virtualized code is left virtualized.

## Verification

`NeverDUnpackTests` checks identification. `NeverDUnpackExecutionTests` unpacks checked-in UPX fixtures (NRV2B, NRV2D, NRV2E, LZMA and a C runtime program) on Unicorn, KVM and WHP, compares every section with the original, runs the recovered image and requires identical bytes from every backend. `UnpackGeneratedTests.cpp` packs a program inside the test for x86-64 and ARM64 and checks a loader that leaves, a loader that first calls into the program and a two-stage loader against the linked file. `NeverDUnpackPublicTests` covers the C ABI and CLI. `unittests/unpack/fixtures/Makefile` regenerates the UPX fixtures.

# Эмуляция гостевых процессов

`neverd emulate` запускает образ с явно заданным профилем гостевой ОС. CPU-транспорт, разбор образа, вход в процесс и службы ОС имеют отдельные границы ответственности. Включите `NEVERD_ENABLE_CPU_EMULATION=ON`; эмуляция драйверов также включает CPU.

Первый профиль `linux-elf64-v1` запускает ELF `ET_EXEC` для x64/AArch64 и саморелокирующие статические PIE `ET_DYN` на CPL3 или EL0. Он загружает реальные сегменты ELF, строит начальный стек, возобновляет выполнение квантами и обрабатывает явные запросы системных вызовов Linux. Это самостоятельная модель процесса, а не полная дистрибуция Linux и не обещание запуска произвольных бинарников libc. Динамическая линковка, сигналы, потоки, файловые системы и неподдерживаемые службы явно приводят к ошибке.

## CLI и SDK

```bash
neverd emulate guest.elf --profile=linux-elf64-v1 \
  --options='{"backend":"auto","arguments":["guest","argument"],"environment":["MODE=test"],"instruction_limit":100000}'
```

Совместимый Linux-хост выбирает KVM, Windows-хост — WHP; другие сочетания ISA хоста/гостя используют Unicorn. Недоступный выбранный бэкенд приводит к ошибке без скрытой подмены. Даже на Windows ELF выполняется в модели Linux-процесса. Перечень инструкций и ограничения описаны в разделе [выполнение CPU](cpu-execution.md).

CLI выдаёт один JSON-отчёт. Код 0 означает нулевой статус гостя, 2 — иной статус, 3 — неполное выполнение (включая сбои и лимиты), 1 — неверная настройка/API. Реальный статус гостя находится в `exit_status`. Добавленная точка C [`neverd_emulate_process_json`](../../include/neverd/sdk/NeverDCAPIProcess.h) принимает сессию, непустой путь, явный профиль и необязательный JSON параметров. Результат освобождается через `neverd_free_string`; NULL означает ошибку настройки, подробности — `neverd_last_error`. Сбой гостя или остановка по ресурсам всё равно возвращают отчёт. Загруженный образ анализа не требуется и не изменяется.

```python
report = session.emulate_process(
    "guest.elf", "linux-elf64-v1",
    '{"backend":"unicorn","arguments":["guest"],"environment":[]}',
)
output = bytes.fromhex(report["stdout_hex"])
```

## Параметры и результаты

Параметры — JSON-объект размером до 64 KiB. Неизвестные/null-поля, неверные типы, встроенный NUL и неположительные лимиты отклоняются.

| Параметр | По умолчанию | Контракт |
|---|---|---|
| `backend` | `auto` | `auto`, `unicorn`, `kvm` или `whp` |
| `arguments` | Имя файла | Полный argv, включая argv[0]; пустой список выбирает значение по умолчанию |
| `environment` | `[]` | Явные строки гостя; окружение хоста не наследуется |
| `instruction_limit` | 100000 | Общее число допущенных попыток инструкций |
| `event_limit` | 10000 | События syscall, учитываемые до обработки службы |
| `timeout_microseconds` | 5000000 | Монотонный deadline после настройки процесса |
| `memory_limit` | 67108864 | Бюджет физической/отображённой памяти |
| `stack_size` | 1048576 | Стек с выравниванием по странице в рамках бюджета |
| `output_limit` | 1048576 | Общий объём stdout/stderr в байтах |
| `instruction_quantum` | 1024 | Интервал допуска до возврата runtime |
| `linux_kernel` | Не задано | Явная ветка GKI, фиксированный каталог гостевых задач или наблюдения отсутствующих интерфейсов ядра |
| `linux_priority` | Не задано | Явные значения nice для задач и полномочия вызывающего для сырых служб приоритета Linux |

`schema_version` равен 1. Отчёт содержит профиль, архитектуру, выбранный бэкенд и причину, `stop_reason`, nullable `exit_status`, диагностику, входной/текущий PC, счётчики, записи служб и последний типизированный выход CPU. Адреса, syscall-номера, регистры аргументов и биты возврата — hex-строки **без** `0x`; `stdout_hex`/`stderr_hex` сохраняют NUL и некорректный UTF-8. Результат syscall null означает отсутствие моделируемого возврата (например, exit или неподдерживаемый запрос), а не успешный ноль.

## Семантика профиля Linux

`writev` использует те же потоки на x64/ARM64 и через Android Bionic. До вывода импортируются до 1024 гостевых записей `iovec`; отрицательная длина даёт `EINVAL`, проверяются пользовательские диапазоны и применяется страничный лимит передачи Linux. Неверный дескриптор даёт `EBADF` до чтения вектора, недоступные метаданные — `EFAULT` без вывода. Поздний сбой данных сохраняет скопированный префикс. Бюджет до публикации охватывает весь вектор и оба потока. `write` и `writev` используют младшие 32 бита дескриптора; число записей тоже соответствует 32-битному импорту Linux. Только Bionic преобразует отрицательные ошибки в `-1` и `errno`. `LinuxOutputNativeTests` запускает десять собственных сценариев на Linux хоста с обычными файлами для вывода; модельные x64/ARM64-тесты дополнительно проверяют бюджеты. См. [контракт импорта Linux](https://github.com/torvalds/linux/blob/v6.12/lib/iov_iter.c).

Политика ОС использует декодированные заголовки программ существующего ELF-загрузчика. Она проверяет ABI-теги, выравнивание сегментов, отображённые таблицы заголовков и границы пользовательских адресов. План отображения проверяет диапазоны, права, пересечения и бюджет до выделения памяти и публикует только полностью подготовленное частное адресное пространство. Сохраняются префиксы/хвосты файловых страниц, BSS обнуляется, права сегментов соблюдаются, для стека резервируются защитные промежутки. Пересекающиеся страницы и противоречивые заголовки отклоняются, а не угадываются.

Статический PIE использует детерминированный load bias не ниже `0x40000000`, увеличивая его для большего выравнивания `PT_LOAD`. Сегменты, PC входа и `AT_PHDR`/`AT_ENTRY` используют один bias; исходные program-header значения не меняются, а без интерпретатора `AT_BASE` равен нулю. Отображаются исходные байты файла, без analysis-fixup; релокацию и инициализацию выполняет сам гость. Загрузчик декодирует `PT_DYNAMIC` из ограниченных записей исходного файла без зависимости от section headers. Если таблица есть, она должна быть читаемой, завершённой и содержать не более 4096 записей. `PT_INTERP` и внешние теги зависимостей/filter/audit отклоняются; dynamic linker, разрешение символов и конструкторы не предоставляются.

Начальный стек содержит выровненные argc/argv/envp/auxv, PHDR/PHENT/PHNUM, entry, размер страницы и идентификаторы. Моделируемые PID/TID/UID/GID равны 1000. Для воспроизводимости `AT_RANDOM` содержит первые 16 байт SHA-256 входа; это детерминированная политика модели, не криптографическая энтропия. HWCAP/HWCAP2 равны нулю; vDSO отсутствует.

Реализованы `write`, `writev`, `exit`, `exit_group`, `getpid` и `gettid`, `mmap`, `mprotect`, `munmap`, `brk` с отдельными номерами для [x64](https://github.com/torvalds/linux/blob/master/arch/x86/entry/syscalls/syscall_64.tbl) и [ARM64](https://github.com/torvalds/linux/blob/master/include/uapi/asm-generic/unistd.h). Возврат x64 SYSCALL применяет clobber RCX/R11, RAX и следующий PC. ARM64 использует x8 для номера, x0 для результата. Неизвестные вызовы останавливаются с `unsupported_service`; системные вызовы хоста не выполняются.

Статические TLS-шаблоны `PT_TLS` проверяются как факты загрузчика: один шаблон, ограниченные файловые/памятные диапазоны, согласованное выравнивание и читаемые инициализированные байты. Старт гостя выделяет и инициализирует TLS-блоки и устанавливает указатель потока; модель Linux не выдумывает libc-специфичный TCB/DTV. Это поддерживает compiler-generated local-exec TLS во freestanding-программах. Динамический TLS и потоки ОС вне объёма.

На x64 `arch_prctl` поддерживает `ARCH_SET_FS`, `ARCH_GET_FS`, `ARCH_SET_GS`, `ARCH_GET_GS`. Set принимает user-range base даже без отображения; последующие разыменования всё равно проверяют права. Kernel-range base возвращает гостевой `EPERM`, неверный Get destination — `EFAULT` без CPU fault. Другие операции явно завершаются ошибкой. ARM64 startup устанавливает `TPIDR_EL0` через `MSR`; `MRS`, обращения FS/GS и восстановление контекста сохраняют указатель потока между квантами и входами backend. Это не реализует планировщик.

Дескрипторы 1 и 2 — виртуальные приёмники байтов. `write` проверяет читаемые пользовательские страницы; если следующая страница недоступна, возвращает читаемый префикс, а если не читается ни байта — `EFAULT`. Неверный дескриптор даёт `EBADF`; запись нуля байтов всё равно проверяет пользовательский диапазон адресов, но не требует отображённой страницы и не читает данные. Атомарность Linux pipe и файлы не моделируются. Превышающая лимит вывода запись останавливается до публикации.

Анонимная память использует то же адресное пространство процесса и физический бюджет, что образ и стек. `mmap` принимает только `MAP_PRIVATE | MAP_ANONYMOUS` с обычными `PROT_NONE`, `PROT_READ`, `PROT_READ | PROT_WRITE`, `PROT_READ | PROT_EXEC` или читаемым RWX. Свободная выровненная подсказка учитывается; иначе поиск промежутков начинается с `0x100000000`, затем с минимального пользовательского адреса, сохраняя защитные области стека. Это детерминированное размещение, не Linux ASLR. Новые страницы независимы и обнулены; частичное снятие отображения может освободить незакреплённые страницы. Проекция CPU или удерживаемое представление backing может продлить жизнь удалённого выделения до конца своей жизни.

Длины округляются до страниц. `munmap` допускает пробелы и повторное удаление; `mprotect` меняет отображённый префикс, затем возвращает `ENOMEM` на пробеле. `PROT_NONE` сохраняет выделение и байты, запрещая гостевой доступ. Сырой `brk` возвращает запрошенную байтовую границу при успехе и прежнюю при отказе, а не ноль/минус один обёртки libc. Начальная граница — выровненный конец образа. Рост учитывает другие отображения и бюджет; сокращение сохраняет байты оставшейся частичной страницы. Правила и приоритеты ошибок следуют Linux [mapping](https://github.com/torvalds/linux/blob/v6.8/mm/mmap.c) и [protection](https://github.com/torvalds/linux/blob/v6.8/mm/mprotect.c).

Файловые, совместные и фиксированные отображения, рост вниз, огромные страницы, блокировка памяти, ключи защиты, режимы только исполнения/записи и другие флаги явно не поддерживаются: остановка до публикации эффектов или выдуманного возврата. Обычные ошибки диапазона, длины и выравнивания в допустимом подмножестве возвращают гостевую ошибку и разрешают продолжение. Гостевые указатели и запросы отображения не передаются ОС хоста.

Необязательный ввод `linux_kernel` задаёт явно наблюдаемое отсутствие интерфейсов ядра. Например, тестовый образ без реализации `pidfd_open` использует:

```json
{"linux_kernel":{"unavailable_syscalls":["pidfd_open"]}}
```

Выбранный прямой вызов возвращает -ENOSYS до проверки аргументов, как отсутствующая точка входа ядра, не создавая дескриптор и не изменяя гостевую память. Обёртка Bionic `syscall` сохраняет обычное преобразование -1/errno. Пропущенный ввод и пустой список сохраняют прежнюю границу неподдерживаемости этого интерфейса; другие неизвестные вызовы не превращаются в ENOSYS. Сейчас допускается только `pidfd_open`; неизвестные имена, повторы и неверные типы отклоняются. Ввод не выводит версию ядра, доступность на хосте или работающую реализацию pidfd. См. [реализацию отсутствующих вызовов ядра](https://github.com/torvalds/linux/blob/master/kernel/sys_ni.c).

Явный `linux_kernel.gki` выбирает выпущенную ветку Android common от 5.10 до 6.18. Реализованы `pidfd_open` для живого модельного процесса и объявленных гостевых задач, а также импорт векторов по версии. Таблица общая с `linux_files`; Bionic и сырые ловушки разделяют владение и порядок ошибок. GKI несовместим с наблюдением отсутствующего `pidfd_open`. Необязательный массив `linux_kernel.tasks` задаёт фиксированный закрытый каталог дополнительных живых задач, например `{ "id": 2000, "group_leader": true }`. Без массива поиск чужих целей не поддерживается; пустой массив знает только текущего лидера группы. PID вне объявленного каталога возвращает ESRCH. Каталог и наблюдения приоритета должны согласовываться; совместное использование с кооперативными потоками Android запрещено. Уровень Android API не выбирает ядро. Восемь исходных ревизий, дескрипторы, тесты и ограничения описаны в [контрактах выпущенных GKI](../android-gki-kernels.md).

Необязательный ввод `linux_priority` объявляет состояние nice тестовых задач с UID вызывающего. Сырые `setpriority` и `getpriority` разделяют это состояние между Linux ELF64 и Android, не меняя приоритеты хоста.

```json
{"linux_priority":{"tasks":[{"id":1000,"nice":0}],
                   "cap_sys_nice":false,"rlimit_nice":0}}
```

Идентификаторы — различные положительные знаковые 32-битные значения; начальное nice лежит в -20..19, а `rlimit_nice` в 0..40. По умолчанию `cap_sys_nice` и `rlimit_nice` равны false и 0, но состояние задач всегда явное. Отсутствующий ввод, необъявленные задачи, включая новые потоки без заданного состояния, и PRIO_PGRP/PRIO_USER останавливают службу как неподдерживаемую без угадывания наследования или владельца. PRIO_PROCESS при who=0 выбирает текущую гостевую задачу, иначе указанную. Неверный селектор возвращает сырой -EINVAL. Запрос установки ограничивает знаковое 32-битное nice диапазоном -20..19. Уменьшение nice требует CAP_SYS_NICE или достаточного RLIMIT_NICE; отказ возвращает сырой -EACCES без изменения состояния. Сырой запрос возвращает `20 - nice`, кодировку ядра 40..1, а не преобразованный результат libc.

[Linux setpriority/getpriority](https://man7.org/linux/man-pages/man2/setpriority.2.html).

`linux_signals` задаёт начальные действия сигналов для всего процесса. Отсутствующая запись неизвестна и не означает `SIG_DFL`; явно пустой список позволяет установить действие без чтения предыдущего. Обязательны все пять полей; беззнаковые 64-битные значения за пределами точного диапазона JSON передаются десятичными строками.

```json
{"linux_signals":{"actions":[
  {"signal":11,"handler":0,"flags":0,"restorer":0,"mask":0}
]}}
```

Номера сигналов — от 1 до 64. `rt_sigaction` и Bionic используют общее состояние, но каждый интерфейс сохраняет свою структуру и порядок ошибок. Ожидающие сигналы, доставка, вызов обработчиков и маски потоков не реализованы; обработчики хоста не используются. См. [полный контракт](../process-emulation.md#linux-profile-semantics).

<a id="windows-pe64-profile"></a>

`linux_kernel.gki` выбирает 5.10–6.18 для `pidfd_open` и векторного импорта; Android API не выбирает ядро. `linux_kernel.tasks` задаёт фиксированные живые задачи как `{ "id": 2000, "group_leader": true }`. Без массива внешние цели не поддерживаются, пустой знает только текущего лидера, вне каталога — ESRCH. Приоритеты должны быть согласованы; кооперативные потоки Android исключены. Таблица общая с `linux_files`; GKI и отсутствующий pidfd несовместимы. См. [полный контракт](android-gki-kernels.md).

Подмножество GKI также включает наблюдаемые CPU-часы процессов и pidfd `ppoll` с нулевым тайм-аутом. Последний требует явного нулевого timespec, null-маски и предела `linux_files`. Записываются только упорядоченные `revents`, без изменения тайм-аута или настенных часов. Закрытый дескриптор даёт POLLNVAL, живой pidfd не готов. Блокирующие ожидания и другая готовность не поддерживаются.

## Явно заданные часы гостевой системы

Необязательный параметр `linux_time` задаёт фиксированные значения для системных вызовов Linux и Android Bionic. Модель не читает часы хоста, не продвигает время при выполнении инструкций и не подставляет время по умолчанию.

```json
{"linux_time":{"clocks":[
  {"id":0,"seconds":"4294967297","nanoseconds":987654321},
  {"id":1,"seconds":123,"nanoseconds":456789}],
  "timezone":{"minutes_west":-60,"dst_time":0}}}
```

Допускаются статические ID 0–9 и 11 и отрицательные CPU-ID выбранного GKI. Дубли идентичности, неизвестные ID и более 16384 образцов отклоняются. Секунды — знаковые 64-битные, для CPU неотрицательные; наносекунды в `[0, 1000000000)`. Целые JSON ограничены `±9007199254740991`, десятичные строки сохраняют весь диапазон; часовой пояс — знаковый 32-битный. C++ использует `ProcessOptions::LinuxTime`; другие OS-профили отклоняют параметр.

`-16006` — SCHED процесса PID 2000. PROF и VIRT независимы. Текущие SCHED ID 2, -6 (PID ноль) и -8006 (PID 1000) разделяют один образец; алиасы PROF — -8/-8008, VIRT — -7/-8007. Дубли отклоняются даже при равных значениях. CPU-секунды неотрицательны, наносекунды нормализованы. Продвижение при простое меняет только настенные часы 0, 1 и 7; CPU-образцы остаются фиксированными. Расход CPU из выполнения инструкций не выводится.

`advance_on_idle: true` включает относительный `nanosleep` x64/ARM64 и именованные/variadic обёртки Android. Настенные часы 0, 1 и 7 могут сосуществовать с фиксированными CPU-образцами; другие виды при этой политике исключены. Готовые потоки исполняются первыми; когда все заблокированы, время достигает ближайшего срока. Единственный поток продвигается прямо. Динамические/FD/кодированные потоковые часы не поддерживаются.

Собственный TID текущей задачи также обозначает её группу, включая кооперативные потоки Android без внешнего каталога. Отсутствующий внешний PID или живой не-лидер в замкнутом каталоге даёт `EINVAL` до доступа к выходу. Неуказанный каталог или отсутствующий образец известной группы оставляет операцию неподдерживаемой до копирования. Неверный вид даёт `EINVAL`; допустимый образец может дать `EFAULT` при пользовательском копировании. Сырые traps сохраняют отрицательные ошибки; только Bionic меняет errno и возвращает -1. [GKI](android-gki-kernels.md).

## Явные файлы в памяти

`linux_files` задаёт закрытый каталог неизменяемых файлов для Linux ELF64 и Android. Обязательный массив `files` может быть пустым; запись требует канонический абсолютный `path` и двоичные `bytes_hex`. Файлы хоста и неявные данные `/proc` не читаются. Без опции файловые службы не моделируются; отсутствующий путь возвращает `ENOENT`.

```json
{"linux_files":{"files":[
  {"path":"/fixture/data","bytes_hex":"00ff410a805a"}],
  "descriptor_limit":256}}
```

Каждое открытие имеет отдельную позицию; Bionic, `syscall`, ловушки и гостевые потоки используют общие дескрипторы. Закрытие освобождает минимальный номер для повторного использования. Поддерживаются `open/openat` только для чтения, `read/close`, обычный `lseek`, `O_CLOEXEC` и архитектурный `O_LARGEFILE`. Только Bionic преобразует errno. Ошибка чтения сохраняет скопированный префикс. Содержимое stdin не задано; относительные пути, каталоги, запись и ссылки исключены.

C++: `ProcessOptions::LinuxFiles`. `descriptor_limit`: 3–4096 (256); `files` ≤ 256; `path` < 4096 bytes; component ≤ 255 bytes; data + paths + NUL ≤ 16 MiB; JSON ≤ 64 KiB. [Contract](../process-emulation.md#explicit-memory-files).

Чтение нулевой длины может начинаться на границе пользовательского адресного пространства. После проверки исходного диапазона адресов сумма позиции файла и исходной длины запроса, превышающая `INT64_MAX`, приводит к `EINVAL` даже при EOF; позиция не меняется.

Запись может содержать полные `metadata`; C++ использует `LinuxFileOptions::Metadata` с уже существующими путями. `fstat`/`fstat64` и syscall разделяют фиксированные наблюдения, не читают метаданные хоста, не выводят size из длины байтов и не меняют позицию. Допускаются обычные файлы и все обязательные поля; полноразрядные целые передаются десятичными строками. x64/AArch64 записывают 144/128 байт, rdev и заполнение равны нулю. Неверный дескриптор даёт `EBADF`, полностью недоступный для записи вывод — `EFAULT`. Отсутствующие метаданные, неизвестные стандартные потоки и смешанные права записи останавливают исполнение без изменения байтов. Поля и границы описаны в указанном контракте.

```json
{"linux_files":{"files":[{"path":"/fixture/virtual","bytes_hex":"616263",
  "metadata":{"device":1,"inode":"18446744073709551615","mode":33060,
    "link_count":1,"uid":1000,"gid":1000,"size":0,"block_size":4096,"blocks":0,
    "access_time":{"seconds":0,"nanoseconds":0},
    "modification_time":{"seconds":0,"nanoseconds":0},
    "change_time":{"seconds":0,"nanoseconds":0}}}]}}
```

## Профиль Windows PE64

`windows-pe64-v1` поддерживает ограниченные консольные процессы Windows x64/ARM64 с PEB/TEB, статическим и динамическим TLS, `DllMain`, именованными Win32 API и явно заданными ациклическими графами DLL. Поддерживаются импорты кода/данных по имени и ординалу, DIR64, перенаправленные экспорты и реальные списки загрузчика. `LoadLibraryA` / `LoadLibraryW`, `FreeLibrary` и `GetProcAddress` используют настроенный каталог. CRT/GUI, SEH ARM64 на основе кадров стека, потоки и общая совместимость с Windows не завершены; нативных свидетельств ARM64 KVM/WHP пока нет.

`WindowsProcessTime.cpp` обслуживает `GetSystemTimeAsFileTime`, `GetTickCount`, `QueryPerformanceCounter`, `QueryPerformanceFrequency` и `ZwDelayExecution` на основе часов хоста. FILETIME измеряется в единицах 100 ns с 1601 года; счётчик производительности использует монотонные часы и заявленную частоту 10 MHz, а миллисекундные тики переполняются по 32 битам. Поддерживаются неуведомляемые относительные задержки до 500 ms и нулевой интервал; уведомляемые ожидания, положительные абсолютные даты и более долгие задержки явно останавливают выполнение без сокращения ожидания или возврата успеха. Сервисы сохраняют LastError и используют одну модель для всех CPU-бэкендов. `ZwDelayExecution` читает только младшие 8 бит `BOOLEAN`; неиспользуемые старшие биты регистра аргумента не влияют на политику ожидания.

[Windows x64 ABI](https://learn.microsoft.com/cpp/build/x64-calling-convention), [QueryPerformanceFrequency](https://learn.microsoft.com/windows/win32/api/profileapi/nf-profileapi-queryperformancefrequency), [FILETIME](https://learn.microsoft.com/windows/win32/api/minwinbase/ns-minwinbase-filetime).

Виртуальная память Windows поддерживает `VirtualAlloc`, `VirtualFree`, `VirtualProtect`, `VirtualQuery` и `FlushInstructionCache` для текущего процесса. Уровень ОС управляет резервированием; `AddressSpace` остаётся единственным владельцем отображений подтверждённых страниц, прав доступа и физической памяти. Тесты проверяют изменение кода, ошибки доступа и повторное использование лимита памяти.

`WriteProcessMemory` воспроизводит измеренное на x64/ARM64 поведение страниц в состоянии MEM_COMMIT при записи до 4 КиБ в текущий процесс. Сохраняются защита каждого региона, скопированные префиксы, число байтов и LastError, включая `ERROR_NOACCESS`, `ERROR_PARTIAL_COPY` и успешный результат после префикса RX. `WindowsMemoryWriteTests.cpp` проверяет все 25 пар защиты; `check_windows_memory_write.py` проверяет тот же оригинальный исполняемый файл в CI на настоящей Windows. Целевые страницы без MEM_COMMIT явно не поддерживаются.

Частные выделения поддерживают `MEM_RESERVE`, `MEM_COMMIT`, `MEM_DECOMMIT`, `MEM_RELEASE` и `MEM_TOP_DOWN`: выравнивание резервирования — 64 KiB, размер страницы — 4 KiB. Резервирование не расходует RAM гостя. Повторное подтверждение сохраняет данные и обновляет права; снятие подтверждения освобождает отдельные страницы. Проверка всего диапазона и предварительное выделение предотвращают частичные изменения при обычных ошибках. Запрос возвращает 48-байтовую структуру x64/ARM64 и объединяет последующие страницы только в пределах одного выделения. Размещение учитывает образ, окружение, кучу, входы API и границы стека; идентичность стека согласована с TEB. Если успешный `VirtualProtect` делает буфер прежних прав доступным только для чтения, новые права остаются установленными, содержимое буфера не меняется, а вызов возвращает успех. Ошибка смены прав для диапазона с неподтверждёнными страницами возвращает `ERROR_INVALID_ADDRESS`, записывает `PAGE_NOACCESS` в буфер прежних прав и оставляет права страниц неизменными.

Поддерживаются `PAGE_NOACCESS`, `PAGE_READONLY`, `PAGE_READWRITE`, `PAGE_EXECUTE_READ` и `PAGE_EXECUTE_READWRITE`. Защитные страницы, только исполнение, копирование при записи, атрибуты кэша, большие страницы, reset/write-watch/заполнители и изменения служебных отображений модели явно не поддерживаются. Снятие подтверждения и освобождение разрешены только для частных виртуальных выделений.

[VirtualAlloc](https://learn.microsoft.com/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc), [VirtualFree](https://learn.microsoft.com/windows/win32/api/memoryapi/nf-memoryapi-virtualfree), [VirtualProtect](https://learn.microsoft.com/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect), [VirtualQuery](https://learn.microsoft.com/windows/win32/api/memoryapi/nf-memoryapi-virtualquery), [MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/windows/win32/api/winnt/ns-winnt-memory_basic_information).

```bash
neverd emulate guest.exe --profile=windows-pe64-v1 \
  --options='{"backend":"auto","arguments":["guest.exe","argument"],"environment":["MODE=test"]}'
```

Однопоточный PE32+ EXE сохраняет предпочтительную базу и допускает явно заданные DLL с необязательной точкой входа и статическим TLS. `WindowsProcessOptions::Modules` или JSON `windows.modules` задаёт до 64 гостевых базовых имён и входных путей через `name` и `path`, без поиска и исполнения DLL хоста. Регистр ASCII-имён не учитывается; дубликаты и подмена системных поставщиков запрещены. Читаются лишь достижимые файлы. Импорты по имени/ординалу связываются с реальными экспортами; пропуски, отсутствующие символы, циклы, bound/delay imports и неподдерживаемая load configuration/CFG отклоняются. DIR64 перемещает допускающие это DLL при конфликте; фиксированные конфликты и релокации в метаданные связывания отвергаются до публикации соответствующего образа.

`readPEProgramExports` владеет исходными экспортами и диапазонами чтения; `WindowsProcessModules` — графом и общими шлюзами API по поставщику/имени. `VirtualMemory` резервирует все образы до отображения; `AddressSpace` владеет страницами и правами. PEB/LDR содержит реальные образы; список инициализации сохраняет порядок регистрации загрузчиком отдельно от порядка вызовов attach по зависимостям. `GetModuleHandleW` принимает NULL либо базовое ASCII-имя, игнорирует регистр и добавляет `.dll` при отсутствии расширения. Пути, не-ASCII и завершающая точка пока не поддерживаются. Отсутствие имени даёт ошибку 126; успех сохраняет LastError. Модели API не являются установленными DLL.

Суммарные входные байты и размеры образов отдельно ограничены `memory_limit`; отображения среды тоже входят в бюджет образов. Подготовка делит лимиты 65,536 записей, 64 MiB чтений метаданных, длины имён и общий срок, без жёсткой гарантии времени I/O хоста. Авторский EXE→DLL→DLL проверяет перебазирование, ординалы, общие данные, идентичность API, `MEM_IMAGE`, списки и attach/detach TLS EXE. `NeverDWindowsProcessTests` включает нативный Windows-оракул, `NeverDPEProgramExportsTests` — повреждённые метаданные и бюджеты, `NeverDProcessPublicTests` — совпадение C ABI/CLI. Недоступные транспорты явно пропускаются.

`WindowsProcessLifetime` выполняет TLS и затем `DllMain` DLL в порядке зависимостей, после чего TLS и вход EXE, на одном CPU с общим бюджетом. Каждый модуль получает отдельный индекс TLS и выровненный блок из перемещённого, связанного образа в общей области 64 KiB. Резервный аргумент TLS равен нулю; `DllMain` при запуске/завершении процесса получает непрозрачное ненулевое значение. Явный выход отсоединяет успешно инициализированные DLL в обратном порядке списка загрузчика, затем TLS EXE, даже до инициализации EXE. Начальный `DllMain(FALSE)` завершает процесс с `0xc0000142` без detach. Ошибки и исчерпание бюджета не имитируют очистку. Возврат из PE-входа с гостевыми DLL требует неподдерживаемого завершения потока и явно останавливается. Ненулевой `SizeOfZeroFill` пока не поддержан; нулевые байты фактического TLS-шаблона поддержаны. DLL без входа получают TLS attach, но не уведомления process detach.

`WindowsProcessExports` использует единое разрешение имён/ординалов для статического импорта и `GetProcAddress`, включая код, данные, псевдонимы и цепочки перенаправлений. Только используемые стартовые перенаправления добавляют модули каталога и зависимости инициализации; остальные не загружают файлы. Имена чувствительны к регистру; отсутствующее имя возвращает NULL/ошибку 127, непосредственно запрошенный отсутствующий ординал (включая пробелы таблицы) NULL/ошибку 182, а аргумент запроса NULL — ошибку 87, успех сохраняет LastError. Неизвестные дескрипторы модулей не поддерживаются. Точные API-входы поставщик/имя резервируются один раз по ограниченному реестру. Проверяются текущие PE-заголовки и метаданные экспорта каждого образа; изменения и нечитаемые байты отклоняются. Цепочки ограничены 64 элементами, используют остаток общего бюджета метаданных и общий срок выполнения. Перенаправление на пустой элемент возвращает базу целевого образа и сохраняет LastError; на нулевой ординал — ошибку 87. База является адресом данных и не даёт права выполнять заголовки образа. Перенаправления во время исполнения могут загружать настроенные модули и завершать инициализацию до возврата результата. Изменение активных таблиц экспорта не поддерживается.

`WindowsProcessLoader` загружает базовые ASCII-имена DLL из `windows.modules` и управляет явными ссылками, общими зависимостями и удержанием стартовых модулей. Повторные запросы перенаправлений не добавляют ссылок. При повторной загрузке слот каталога получает новое поколение резидентности. TLS и `DllMain` исполняются на том же CPU ниже приостановленных кадров API; восстановление регистров сохраняет записи гостя и использует текущий адрес возврата. Резервные указатели динамических attach/detach равны нулю. Неудачный attach при явной загрузке возвращает 1114 после очистки, сохраняя успешные независимые вложенные загрузки. Выгрузка освобождает образ и TLS, повторная загрузка восстанавливает исходные байты. Внешние изменения списков загрузчика и указателей TLS явно отклоняются. Бюджеты файлов, образов и метаданных остаются накопительными после ошибок и перезагрузок. Системные поставщики используют базы отображённых PE как дескрипторы модулей. Поиск файлов, пути не ASCII, флаги `LoadLibraryEx`, циклы и повторный вход для переходов того же инициализируемого или выгружаемого модуля не поддерживаются.

DLL как вход процесса использует `WindowsLibraryHost.cpp`: моделируемый PE EXE выполняет `LoadLibraryA` → `FreeLibrary` → `ExitProcess` на том же гостевом CPU. Вход занимает одно из 64 мест каталога, сохраняет базовое имя и разделяет бюджеты подготовки и исполнения с хостом и зависимостями. `GetModuleHandle(NULL)` указывает на хост; `GetModuleFileNameA` принимает дескрипторы резидентных модулей. Открытие собственного файла ограничено явным входным файлом. Ошибка присоединения следует обычному коду 1114 и очистке; сигнатуры экспортов не угадываются.

`GetEnvironmentVariableW`, `SetEnvironmentVariableW`, `GetEnvironmentStringsW`, `FreeEnvironmentStringsW`, `ExpandEnvironmentStringsW` используют текущий блок окружения гостя из параметров процесса PEB. Имена ASCII сравниваются без учёта регистра; значения представлены в UTF-16. Перед изменением проверяются входные данные, ёмкость и права записи. Снимки не зависят от последующих изменений и освобождают гостевую память. Модель ограничивает блок 64 KiB; строки и подстановка ограничены по размеру и проверяют срок выполнения. Неизвестная принадлежность указателей, некорректные блоки, кодовые страницы ANSI и перекрывающиеся буферы подстановки не поддерживаются. `WindowsEnvironmentTests.cpp` сравнивает оригинальные фикстуры x64/ARM64 на доступных бэкендах; CI требует независимый нативный оракул Windows.

`WindowsProcessHeap` объединяет выделение, [`HeapReAlloc`](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heaprealloc), освобождение и запрос размера блоков кучи процесса. Изменение размера сохраняет оставшиеся байты; `HEAP_ZERO_MEMORY` обнуляет добавленные байты, а `HEAP_REALLOC_IN_PLACE_ONLY` запрещает перемещение. При неудачном изменении размера старый блок сохраняется, возвращается NULL и устанавливается `ERROR_NOT_ENOUGH_MEMORY` (8), как в нативных наблюдениях. Независимые страницы возвращают ёмкость при уменьшении и освобождении; подготовка роста и ограниченное копирование проверяют срок выполнения. Собственные кучи, флаги исключений, неизвестная принадлежность и недоступные диапазоны явно останавливают выполнение. `WindowsHeapTests.cpp` проверяет обе ISA, принудительное перемещение, повторное использование бюджета и атомарность ошибок; CI также запускает тот же оригинальный EXE на нативном Windows.

`windows.peb_version` явно задаёт поля PEB `major`, `minor`, `build` и `platform`. Обязательны все четыре беззнаковых целых: `build` имеет ширину 16 бит, остальные — 32 бита. При отсутствии параметра поля версии профиля остаются нулевыми. Их инициализацией на x64 и ARM64 владеет `WindowsProcessEnvironment`. Параметр не выбирает номера системных служб и не подтверждает совместимость с указанной версией Windows. Байты окружения, от которых зависит сохранённый код, должны совпадать при захвате и нативном выполнении.

`WindowsSystemModules` создаёт ограниченные модельные PE64-образы `ntdll.dll`, `kernelbase.dll` и `kernel32.dll` для обеих ISA. ASCII-запросы `GetModuleHandleA` / [`GetModuleHandleW`](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandlew), `LoadLibraryA` / `LoadLibraryW` и [`GetProcAddress`](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress) используют общие отображённые базы; PEB/LDR и `MEM_IMAGE` описывают те же образы. Статические импорты, поиск по имени и гостевые перенаправления используют единые API-переходы и разрешение экспортов. Поставщики закреплены в памяти, не имеют гостевых обработчиков инициализации и не мешают возврату из точки входа после выгрузки обычных гостевых DLL. Изменение заголовков или метаданных экспортов останавливает поиск. Неизвестные системе модели имена и ненулевые системные ординалы явно отклоняются; отличие только регистра известного имени и пустое имя возвращают ошибку 127, NULL-запрос — 87. Созданные байты и адреса определяет модель; расположение конкретных версий Windows, нативные ординалы и межмодульные псевдонимы не воспроизводятся. `WindowsSystemTests.cpp` сравнивает оригинальные x64/ARM64 EXE с нативным Windows, включая восемь независимых наблюдений возврата начального потока.

`WindowsProcessExceptions` реализует `AddVectoredExceptionHandler`, `RemoveVectoredExceptionHandler` и `RaiseException` на одном CPU с общим бюджетом процесса. Упорядоченные обработчики могут менять регистрации, вызывать вложенные исключения, модельные API, загрузку DLL и завершение процесса. Нарушения доступа к данным x64/ARM64 и ошибки целочисленного деления x64 допускают продолжение после проверки изменений гостя в `CONTEXT`; сохраняются общие регистры, SIMD и поддерживаемое FP-состояние. Программные исключения продолжаются через настоящую инструкцию возврата модельного поставщика. Пределы: 128 сохраняемых регистраций и 16 вложенных кадров. Неверные результаты, изменённые указатели, неподдерживаемые поля и превышения явно отклоняются. SEH/раскрутка ARM64 по кадрам стека, отладчик и ошибки исполнения/защитных страниц не поддерживаются. `WindowsExceptionTests.cpp` сравнивает оригинальные EXE/DLL с нативным Windows; нативных доказательств ARM64 KVM/WHP пока нет. [AddVectoredExceptionHandler](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-addvectoredexceptionhandler), [RemoveVectoredExceptionHandler](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-removevectoredexceptionhandler), [RaiseException](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-raiseexception), [CONTEXT x64](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-context), [ARM64_NT_CONTEXT](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-arm64_nt_context). Записи программных исключений содержат `EXCEPTION_SOFTWARE_ORIGINATE` (`0x80`) независимо от переданного вызывающей стороной флага запрета продолжения; исходный исполняемый файл Windows проверяет точные значения флагов программных и аппаратных исключений. [EXCEPTION_RECORD](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-exception_record).

`WindowsProcessContext` сохраняет происхождение каждого кадра диспетчеризации. Поддерживаемые ошибки x64 при доступе к данным и делении показывают RF (`0x10000`) в `CONTEXT.EFlags`; `RaiseException`, включая программные коды нарушения доступа, сохраняет текущий контекст. Происхождение сохраняется при VEH/VCH и поиске/раскрутке SEH. Допустимое продолжение восстанавливает логические флаги CPU без RF; изменения RF гостем отклоняются до публикации состояния. Этот ограниченный профиль не моделирует точки останова на инструкциях или управление RF гостем. `WindowsExceptionTests.cpp` проверяет записи, восстановление и неизменность CPU/RAM при отказе.

По независимым нативным наблюдениям Windows ring3 преобразует ошибки checked x64 `operand_alignment` в `STATUS_ACCESS_VIOLATION` с параметрами `[read, UINT64_MAX]`, включая записи. Причину предоставляет слой CPU; Windows не угадывает её по вектору 13 и не декодирует инструкцию повторно. `WindowsAlignmentProcessTests.cpp` выполняет исходные PE-инструкции в 72 сценариях ошибки и 9 повторах после исправления адреса (`72 + 9`), проверяя PC, RF, XMM и RAM. Неклассифицированные или противоречивые ошибки отклоняются. Отчёты процессов и драйверов сохраняют nullable-поля `cause` и шестнадцатеричное `error_code`, различая отсутствие и ноль. Эта доставка относится к пользовательскому профилю checked x64.

`AddVectoredContinueHandler` и `RemoveVectoredContinueHandler` ведут отдельный упорядоченный список; обе группы обработчиков делят предел в 128 сохраняемых регистраций. После согласия векторного обработчика исключения на продолжение обработчики продолжения получают ту же изменяемую запись исключения и `CONTEXT`. Итоговая проверка контекста выполняется после этих вызовов, включая вложенные исключения и уведомления DLL. Удалять дескрипторы через API другой группы нельзя. `WindowsContinuationTests.cpp` сравнивает собственные EXE с нативным Windows: порядок, досрочное завершение, изменение регистраций, восстановление контекста, вложенность, вызовы загрузчика и выход процесса. Проверенный векторный путь Windows x64 допускает продолжение при `EXCEPTION_NONCONTINUABLE`; это не доказывает поведение SEH по кадрам стека. Нативное исполнение ARM64 ещё не проверено. [AddVectoredContinueHandler](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-addvectoredcontinuehandler), [RemoveVectoredContinueHandler](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-removevectoredcontinuehandler).

`RtlCaptureContext` доступен через `kernel32.dll` и `ntdll.dll` для x64 и ARM64. Общие `WindowsProcessContext` и `IntegerABI` сохраняют PC/SP вызывающего кода, не меняя состояние CPU и LastError. Нативные наблюдения Windows подтверждают флаги x64 `0x10000f`, сохранение незаписываемых областей home/отладки/векторов и старые 32-битные поля адресов x87; ARM64 копирует LR в PC и обнуляет X0/LR в записи. Регистры, SIMD и управление плавающей точкой берутся у гостя; селекторы x64 и маска возможностей MXCSR соответствуют настроенному гостевому CPU. Некорректные, невыровненные или частично недоступные буферы отклоняются до записи. `WindowsContextTests.cpp` проверяет прямой импорт, поиск у поставщика, вызовы VEH, запись через границу страниц и атомарность ошибок. `scripts/check_windows_context.py` запускает оригинальную программу в Windows x64/ARM64 и отдельный нативный оракул непустого состояния x87. Эти наблюдения ARM64 API не доказывают нативное выполнение KVM/WHP. Восстановление контекста, обход стека и динамические таблицы функций остаются отдельными задачами. `WindowsProcessServices.def` задаёт точные ограничения по модулям: поиск в `kernelbase.dll` возвращает `ERROR_PROC_NOT_FOUND` (127), как и в нативных наблюдениях, без добавления несуществующего экспорта. [RtlCaptureContext](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-rtlcapturecontext).

`WindowsProcessSEH` использует общий `X64SEH` в `os/windows/exception/` (`NeverDEmulationWindowsException`, доступен без драйверов) для x64 `__C_specific_handler` и UNWIND_INFO V1. После поиска VEH поддерживаются фильтры, finally, нелокальный переход к обработчику, вложенная/конфликтующая раскрутка и перемещённые кадры EXE/DLL с сохранением сохраняемых GPR/XMM. Продолжение из фильтра вызывает VCH с тем же `CONTEXT`. `WindowsSEHTests.cpp` сравнивает 23 собственных сценариев с нативным Windows; KVM/WHP/Unicorn используют общую семантику. Бюджет процесса ограничивает повторную проверку поколений образов, заголовков, байтов раскрутки/областей, кода языкового обработчика и привязок IAT. Изменённые метаданные или выгруженные удерживаемые образы явно отклоняются. Кадровый SEH ARM64, C++ EH, динамические таблицы функций, общие RtlUnwind/NtContinue и раскрутка через границы вызовов загрузчика/VEH/VCH пока не поддерживаются.

Для `EXCEPTION_NONCONTINUABLE` возврат `EXCEPTION_CONTINUE_EXECUTION` из фильтра x64 вызывает `STATUS_NONCONTINUABLE_EXCEPTION` (`0xc0000025`, флаги `0x81`, связанная запись null) с новым контекстом. VEH запускается повторно перед поиском по сохранённому логическому стеку; порядок finally, идентичность кадров EXE/DLL и бюджеты глубины и исполнения сохраняются. Из 23 нативных сценариев 21 завершается успешно, а два приводят к прекращению процесса: согласие VEH/VCH продолжить вторичное исключение оставляет его необработанным даже после восстановления исходного `CONTEXT`. Модель сообщает об ошибке выполнения. Адрес программного исключения совпадает с сохранённым PC; внутренние адреса диспетчера и раскладка регистров определяются моделью. [Windows x64 CI](https://github.com/NeverSight/NeverD/actions/runs/37141166235).

Перед обратными вызовами динамической выгрузки модуль удаляется из списка инициализации; отображение, поиск по имени и принадлежность к спискам загрузки/памяти сохраняются на время вызовов. Нативные проверки возврата из точки входа наблюдают начальный поток независимо от рабочих потоков системы.

`WindowsDynamicTests.cpp` сравнивает исходные DLL/EXE x64/ARM64 с независимыми наблюдениями Windows: ссылки, общие зависимости, вложенные загрузки, очистка после ошибок, перенаправления, завершение, DLL без точки входа и новый TLS при перезагрузке. Дополнительные проверки отклоняют изменённые метаданные и устаревшие указатели кода, сохраняют накопительные бюджеты и незавершённые результаты прерванных API. Windows CI требует нативный оракул и случаи WHP; кросс-компиляция и Unicorn ARM64 не доказывают нативное исполнение ARM64.

Отсутствие библиотеки в любой позиции цепочки перенаправления `GetProcAddress` возвращает 127; явный `LoadLibrary` для отсутствующего в каталоге модуля возвращает 126. Нативный эталон и каждый доступный backend проверяют все 41 объявленных сценариев. В Windows возврат после выгрузки всех DLL наблюдается 16 раз для каждого варианта DLL. Ошибка инициализации через перенаправление `GetProcAddress` также возвращает 127 после очистки. Обратные вызовы отсоединения процесса сохраняют содержимое стека завершающего вызывающего кода.

`WindowsExportTests.cpp` использует исходные DLL и EXE x64/ARM64 для проверки перенаправленных вызовов кода/данных/ординалов, псевдонимов, запросов при инициализации, перебазирования, регистра, отсутствующих экспортов, LastError, циклов, нерезидентных целей, неверных указателей и изменений после успешных запросов. Тот же EXE выполняется независимым нативным Windows-оракулом; WHP-тесты обязательны в нативном CI. C ABI/CLI сравнивают полные отчёты. Доказательства на нативном оборудовании ARM64 ещё отсутствуют. Варианты EXE с таблицей экспорта и без неё проверяют оба графа, порядок PEB и detach, а также ошибки имени/ординала/NULL.

`WindowsLifetimeTests.cpp` сравнивает фиксированные трассы с независимыми нативными Windows-процессами и KVM/WHP/Unicorn: нормальный выход, возврат из входа, оба отказа DLL, четыре ранних выхода и DLL без входа. Проверяются также ошибки callback, общие бюджеты, перемещённые поля TLS и общая ёмкость. Нативная проверка возврата сохраняет дескриптор начального потока и 64 раза проверяет его код завершения и точную последовательность уведомлений потока/процесса. Оставшиеся дочерние потоки завершаются после наблюдения; код процесса не считается значением возврата из входа.

```json
{"windows":{"modules":[{"name":"middle.dll","path":"inputs/middle.dll"},{"name":"leaf.dll","path":"inputs/leaf.dll"}]}}
```

GS на x64 и x18 на ARM64 указывают на TEB: границы стека, указатель на себя, PID/TID, PEB, параметры, LastError и TLS. Строгий UTF-8 преобразуется в UTF-16, argv экранируется по правилам Microsoft CRT. Имена окружения — ASCII, дубликаты без учёта регистра запрещены; значения допускают Unicode, отсортированный блок завершается двумя NUL. Окружение и файловая система хоста не наследуются. Статический TLS копирует шаблон, обнуляет BSS и записывает 32-битный индекс; динамический TLS использует другие слоты TEB. Attach/detach читает текущий массив последовательно с общими бюджетом и сроком. Нормальное завершение процесса вызывает detach. Возврат из точки входа поддерживается только без резидентных гостевых DLL; повторный `ExitProcess` во время очистки завершения не поддерживается.

`WindowsProcessServices.def` задаёт `ExitProcess`, `RtlExitUserProcess`, выходные дескрипторы и синхронный `WriteFile`, LastError, ID и псевдодескрипторы процесса/потока, `GetCommandLineW` / `HeapReAlloc`, выделение/освобождение/размер кучи, динамический TLS и `LoadLibraryA` / `LoadLibraryW` / `FreeLibrary` / `GetModuleHandleA` / `GetModuleHandleW` / `GetProcAddress`. Разрешаются точные имена из `kernel32.dll`, `kernelbase.dll`, `ntdll.dll`. Прямые syscall и поддельные входы не выбирают API. Куча принадлежит процессу и освобождается; вывод сохраняет бинарные байты. Ошибки Win32 отделены от неподдерживаемых асинхронных операций и пользовательских исключений. Алиасы учитывают первоначальное обнуление счётчика и актуальный адрес возврата.

`windows.native_calls` сохраняет модуль/функцию, объявленные скалярные аргументы и nullable результат без выдуманных номеров NT. `NeverDWindowsProcessTests` проверяет реальные PE, TLS компилятора, изменения callback, кучу, алиасы, повреждённые метаданные, привилегии и бюджеты; `NeverDProcessPublicTests` — CLI/C ABI. Windows CI непосредственно запускает тот же EXE как независимый эталон и требует тесты WHP. Для свидетельств нативного ARM64 по-прежнему нужна соответствующая машина.

Если непустой входной буфер недоступен для чтения, `WriteFile` возвращает `ERROR_INVALID_USER_BUFFER` (1784), обнуляет число записанных байтов и ничего не выводит.

`windows.defer_unmodeled` загружает образ, чьи факты загрузки модель не реализует, и останавливается, только если выполнение зависит от одного из них. Экспорты вне перечня API и модули вне каталога связываются с непрозрачными точками входа: каждая идентичность разрешается в один адрес, а её выполнение останавливается как `unsupported_service` с указанием `module!export`. Каталоги, которые модель не интерпретирует, остаются неинтерпретированными, метаданные, не подкреплённые файлом, при загрузке не читаются, а кадровая диспетчеризация исключений через такой образ останавливается. `observeProcess` добавляет `ProcessObserver`, который читает остановленный процесс при его запуске и на каждом наблюдении за выполнением; он не может изменить состояние гостя, а когда он завершает выполнение, сообщается `observer`. [Распаковка](unpack.md) построена на обоих механизмах.

## Проверка

```bash
cmake --build build-cpu --target NeverDLinuxProcessTests NeverDExecutionSessionTests NeverDX64MemoryUpdateTests NeverDThreadPointerTests --parallel 4
ctest --test-dir build-cpu -L '^NeverD(LinuxProcess|ExecutionSession|X64MemoryUpdate|ThreadPointer)Tests$' --output-on-failure
# Для сборки shared-library/CLI:
cmake --build build-cpu --target NeverDProcessPublicTests --parallel 4
ctest --test-dir build-cpu -L '^NeverDProcessPublicTests$' --output-on-failure
```

Тесты компилируют автономные входы ELF на ассемблере и C для обеих ISA: data/BSS, реальные стартовые данные, ошибки syscall, двоичный вывод, права, частичные записи, неподдерживаемые службы и бюджеты между квантами. TLS инициализирует независимые выровненные блоки, BSS и указатели потока и проверяет их сохранение; x64 проверяет ошибки `arch_prctl` без потери прежней базы. Недоступные backend явно пропускаются. Публичный набор проходит общую C ABI и CLI, сверяя отчёты и коды выхода. PIE проверяет auxv и исходно нулевые RELA-слоты до собственных перемещений данных и функций. Тесты отображения сохраняют fixup при выборе аналитического источника байтов; динамические таблицы проверяются без секций и с неверными/зависимыми входами. Обе ISA проверяют выделение, защиту, пробелы, повторное отображение, рост/сокращение кучи и обработанные ошибки. Настоящие гостевые записи проверяют сбои после обычной и частичной смены защиты. x64 переписывает код по одному адресу между RW и RX и вызывает обе версии; тот же ELF нативно запускается в Linux как независимый оракул результатов и сбоев. Тесты памяти проверяют исчерпание бюджета, освобождение и авторитетные снимки отображений без удержания RAM. Кросс-компиляция и Unicorn ARM64 не доказывают работу нативного ARM64 KVM/WHP.

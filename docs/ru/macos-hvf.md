# Нативное выполнение CPU в macOS (HVF)

NeverD использует [Hypervisor.framework](https://developer.apple.com/documentation/hypervisor) как аналог KVM и WHP для macOS. `--backend hvf` выбирает его явно; `auto` использует HVF для подходящего нативного контракта при совпадении ISA: ARM64 на Apple Silicon и x86-64 на Intel. `software-cpu-v1` и автоматическое выполнение между разными ISA используют Unicorn. Запуск переведённого Rosetta исполняемого файла отклоняется.

Нужны macOS 11 или новее и аппаратная виртуализация; другие зависимости могут требовать более новую ОС. Явно выбранный нативный backend сообщает о недоступности без незаметного переключения. [Virtualization.framework](https://developer.apple.com/documentation/virtualization) управляет целыми виртуальными машинами; NeverD нужны средства управления vCPU, регистрами, отображениями памяти и исключениями из Hypervisor.framework.

## Сборка и подпись

Включите `NEVERD_ENABLE_CPU_EMULATION=ON` или эмуляцию драйверов. `NEVERD_EMULATION_BACKEND_HVF` по умолчанию имеет значение `ON`; framework подключается только в macOS. При `OFF` имя `hvf` остаётся допустимым, но API возможностей возвращает `build_disabled`.

Подключение фреймворка и подпись hypervisor применяются только к целевой системе сборки macOS (`CMAKE_SYSTEM_NAME=Darwin`). Мобильные цели Apple, включая iOS, не получают эту зависимость или разрешение. Гостевой профиль iOS по-прежнему может использовать HVF, если сам NeverD работает на Mac с совпадающей ISA.

Право [`com.apple.security.hypervisor`](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor) требуется **исполняемому файлу процесса**. Подписи одной `libneverd.dylib` недостаточно. CMake подписывает CLI, worker и тесты через `resources/macos/neverd-hypervisor.entitlements`. `NEVERD_HVF_SIGN_IDENTITY` по умолчанию равен `-` для ad hoc; можно выбрать имеющуюся идентичность подписи. Упаковка повторно применяет и проверяет право после исправления зависимостей Mach-O.

Встраивающее приложение подписывает собственный процесс. NeverD не переподписывает установленный Python. `cpu-capabilities --configuration=JSON --probe-host` проверяет реальный процесс. Отдельный worker подписывается по умолчанию; `NEVERD_WORKER_SIGN_HVF=OFF` предназначен только для worker без необходимости HVF.

## Владение ресурсами и выполнение

`backends/hvf/HvfExecutor` владеет одной VM на процесс и одним vCPU. Выделенный поток создаёт, использует и уничтожает их. Логические CPU делят executor и входят последовательно. Перед сменой CPU удаляются два физических отображения прежнего владельца. Уничтожение неактивного CPU не затрагивает чужие отображения. Привязки снимаются синхронно до освобождения RAM; частичная неудачная регистрация откатывается. При ошибке снятия отображений VM завершается до освобождения памяти; неисправимая ошибка уничтожения останавливает процесс.

Отображения хоста используют его размер страницы, включая 16 KiB на Apple Silicon. Архитектурные таблицы страниц и бюджет гостевого CPU остаются 4 KiB. Допуск инструкций, права, состояние CPU, транзакции памяти и службы ОС принадлежат своим слоям. Нативный worker не вызывает гостевые наблюдатели и не захватывает основные блокировки памяти вызывающего кода.

ARM64 пошагово исполняет пять неизменяемых инструкций обслуживания TLB/I-cache, затем допущенную гостевую инструкцию. `PSTATE.D` не маскирует отладочные исключения, направленные в EL2. Полностью сохраняются скалярное состояние, TLS и FP/SIMD. Intel согласует VMCS, использует monitor trap, инвалидирует TLB и переносит полные пакеты XSAVE. RIP/RFLAGS передаются прямо через VMCS, в том числе после пересоздания vCPU. CR0/CR4 учитывают маски framework и обязательные аппаратные биты. Подтверждённые выходы чтения CR8 завершаются слоем ISA; другие обращения к управляющим регистрам отклоняются. Каждый vCPU инициализирует собственный управляемый `IA32_KERNEL_GS_BASE`; гостевые MSR перехватываются, неподдерживаемые MSR/SWAPGS не допускаются.

Очередь соблюдает исходные токен остановки и срок. Подготовка, обслуживание, вход и захват состояния используют единый бюджет. `RunDeadline` ждёт подтверждения прерываний до возврата. Отмена пересоздаёт vCPU, изолируя запоздалые прерывания; посторонние прерывания Intel-хоста повторяются в той же генерации отмены. Ошибки захвата и подтверждённые исключения приоритетнее одновременной остановки; обычное отменённое состояние не публикуется. Отмена кооперативная, без жёсткой гарантии реального времени.

## Проверка

Используйте Release, CMake, Ninja, Python 3, Clang, `ld.lld`, `lld-link`, `ld64.lld` и `codesign`. Линкеры LLVM создают ELF-, PE- и Mach-O-образцы. Отсутствие обязательного нативного образца означает ошибку проверки.

```sh
cmake -S . -B build-hvf -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON \
  -DNEVERD_BUILD_SHARED=OFF -DNEVERD_ENABLE_PYTHON_PLUGINS=OFF \
  -DNEVERD_ENABLE_CPU_EMULATION=ON \
  -DNEVERD_ENABLE_SEMANTIC_TESTS=OFF \
  -DNEVERD_EMULATION_BACKEND_UNICORN=OFF
python3 scripts/run_native_cpu_ci.py --build build-hvf \
  --evidence build-hvf/native-evidence --require-hvf
```

На Apple Silicon можно добавить `-DNEVERD_LLVM_PREBUILT=ON`; Intel собирает закреплённую ревизию LLVM. [Workflow HVF](../../.github/workflows/hvf.yml) поддерживает `self-hosted, macOS, ARM64/X64, hvf` и `hosted-intel` на `macos-15-intel`. Сначала требуется реальное создание и уничтожение VM/vCPU. `validation=probe` не доказывает исполнение инструкций; `transport` проверяет только транспорт; `darwin` требует все подходящие Darwin-нагрузки; `full` требует полные проверки CPU и Darwin.

Транспорт требует 12 тестов ARM64 либо 10 Intel; полный CPU — соответственно 16 либо 14 обязательных результатов. Покрываются полное состояние, привилегии, права, границы страниц, алиасы, переключение CPU, откат, отмена и повторный запуск. Intel проверяет CR8 перед большой сборкой. Артефакты сохраняют инвентарь, ревизию, хост, результаты и отдельные попытки. [GitHub](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners) считает вложенную виртуализацию экспериментальной; для повторяемой приёмки полезен выделенный нативный Mac.

На размещённом Intel `--execution-methods` последовательно запускает каждый метод GoogleTest со всеми параметрами, флагами, окружением и рабочим каталогом CTest. Неизвестные свойства отклоняются. Общий срок метода ограничен 120 секундами, без отдельного срока для каждого параметра; затем группа процессов завершается с ограниченным ожиданием. Сохраняются исходный XML, соответствие имён и код выхода. Тайм-аут или неполный XML дают частичный провал; отсутствие или пропуск обязательного нативного теста не может считаться успехом. Собственные runner сохраняют процессы и сроки CTest для каждого случая.

## Полный инвентарь Intel по частям

Полный запуск `37106679688` завершился 2026-10-03 в 08:35 UTC; GitHub отметил потерю связи с runner. Все четыре задания запуска `37116327329` также потеряли связь и не сохранили CPU XML. Эти факты не позволяют определить сбойную гостевую инструкцию. Режим `full` на размещённом Intel использует четыре задания, не более двух одновременно. Каждое последовательно выполняет четыре пакета: всего шестнадцать частей с номерами `job + 4 × batch`. Исходный набор тестов каждого задания сохраняется. Каждый пакет сначала собирает и проверяет полный инвентарь CTest всех двадцати целей. `--hvf-shard INDEX/COUNT` сохраняет целые методы и все их параметры вместе, даже при разных свойствах исполнения.

До исполнения CPU `scripts/prepare_hvf_batches.py` сохраняет полный и выбранные инвентари и планы методов; workflow отдельно загружает эти диагностические данные. Локальное составное действие выполняет четыре пакета и после каждого сразу загружает исходный XML, отображения имён, состояния процессов и разрешённый перечень нужных переменных среды. Единый внешний срок в 30 минут охватывает все четыре пакета и загрузки. Ошибка пакета останавливает исполнение последующих. После ошибки или истечения срока отдельной диагностической загрузке отводятся две минуты, если runner ещё доступен; при потере связи остаются только уже загруженные свидетельства. Планы и незавершённые диагностические пакеты не считаются пройденными частями.

Отдельное задание Linux запускает `scripts/audit_hvf_shards.py` и заново выводит цели и обязательные нативные проверки из извлечённых исходников. Workflow скачивает только CPU-артефакты текущей попытки; аудит требует все шестнадцать частей одного коммита без локальных изменений, правильную ISA macOS и совпадающие нормализованные контракты исполнения. Результаты должны быть непересекающимися и точно покрывать полный инвентарь; все дочерние процессы и обязательные проверки должны завершиться успешно. Отсутствующая часть, изменённый фильтр, неверная сводка, неполный XML или пропуск обязательной проверки означают провал. Каждое нативное задание сохраняет транспорт, восстановление, CR8 и отдельный контроль Darwin. Собственные runner используют CTest без разделения. Пакетное сохранение само по себе не доказывает приёмку Intel. Повторять нужно все нативные задания; артефакты прежних попыток не объединяются.

Первый проверенный CPU-пакет [запуска `37123148209`](https://github.com/NeverSight/NeverD/actions/runs/37123148209) на чистом исходном коде `f5f29a484` — часть `1/16`: 476 зарегистрированных результатов в 31 процессе методов, из них 82 пройдены, 0 ошибок, 394 пропущены; единственный обязательный нативный случай этой части пройден. Проверен SHA-256 артефакта `11274755752`; исходный XML, статусы завершения процессов, инвентарь и план методов сверены с планом до исполнения. Это частичное свидетельство Intel, которое не завершает полную приёмку CPU.

## Отдельная диагностика Intel

Ручной [диагностический workflow Intel](../../.github/workflows/hvf-intel-diagnostic.yml) извлекает контроллер и проверяемые исходники отдельно. `source-ref` требует полный SHA коммита; `shards` выбирает части исходного разбиения на шестнадцать частей. `first-method` отсчитывается от нуля, `method-count=0` выбирает оставшиеся методы. Через `case-index` можно выбрать один исходный параметр только при `method-count=1`. До выбора определяется полный инвентарь двадцати целей. Сохраняются исходные Release-сборка, команды, параметры и обязательные нативные проверки.

`intel-image`, как и в полном workflow, выбирает по умолчанию `macos-15-intel` или `macos-26-intel` для контролируемого сравнения. Название запуска указывает выбранный образ, а проверка доступности по-прежнему требует нативный хост x86-64. Смена образа затрагивает ОС, SDK и инструменты сборки, поэтому не позволяет отдельно проверить изменение ядра.

Для компиляции выделен отдельный лимит 120 минут в рамках задания на 180 минут: первая полная сборка на macOS 26 заняла 76 минут. Лимит выполнения нативного метода остаётся 120 секунд, а диагностического Action — 30 минут.

Перед каждым методом действие загружает неизменяемый план и снимок состояния хоста. После исполнения сохраняет исходный XML, завершение процессов, состояние контроллера и второй снимок. Фиксируются память, swap, нагрузка, диск, идентификаторы, состояние, CPU, RSS и имена исполняемых файлов процессов, без аргументов и окружения. Ошибки сбора также сохраняются. Ошибка исполнения или загрузки останавливает следующие методы. Лимит каждого метода остаётся 120 секунд; недоступность хоста может помешать очистке и итоговой загрузке. Тогда сохраняются лишь уже загруженные свидетельства. Частичная диагностика не заменяет полную проверку CPU или отдельную проверку Darwin. Последняя начальная отметка указывает границу исполнения, а не сбойную гостевую инструкцию или первопричину.

Полный workflow `Native macOS HVF` также принимает необязательный `source-ref`. По умолчанию используется коммит workflow; явное значение должно быть полным SHA. Нативные задания и сводный аудит извлекают и проверяют одни и те же исходники. Свидетельства сопоставляются с проверяемым коммитом, даже если контроллер имеет другую ревизию.

Для `hosted-intel` полный workflow принимает `intel-image=macos-15-intel` (по умолчанию) или `macos-26-intel`. Оба указаны в [официальном списке образов runner](https://github.com/actions/runner-images). Это позволяет явно сравнивать среды хоста при одинаковом `source-ref`; образ также меняет ОС, SDK и инструменты. Требования к VM/vCPU, нативному транспорту, CR8, полному набору CPU и Darwin не меняются. Сам выбор образа не доказывает стабильность или исправление ошибки выполнения.

`sample-active-child=true` позволяет один раз сохранить неизменяемый снимок через пять секунд после обнаружения регистрации нативного дочернего процесса: секундную выборку стеков проверенного нативного дочернего процесса, до 1 MiB конца его текущего журнала и состояние хоста. Значение по умолчанию — `false`. Для соблюдения лимита artifacts разрешено не более 166 методов на задание с выборкой; команда ограничена двадцатью секундами, а отчёт — 1 MiB. Ошибки проверки процесса и сбора данных сохраняются, в том числе нулевой код выхода без отчёта о стеках. Загрузка выполняется из отдельного неизменяемого каталога; её сбой отменяет нативный дочерний процесс и завершает action с ошибкой. Выборка влияет на планирование и помечается как частичное свидетельство с инструментированием. Она не перезапускает исходный таймер метода и не заменяет полную приёмочную проверку.

Полный workflow также принимает `recovery-repetitions=1000` для целевой проверки прерываний и восстановления; значение по умолчанию остаётся `100`. Этот выбор увеличивает общий лимит шага повторений с трёх до десяти минут. Каждый нативный тест сохраняет исходный срок, проверки и остановку при первом сбое. Заголовок запуска указывает увеличенное число повторений. Они не заменяют полные проверки CPU или Darwin.

Отдельный [workflow диагностики восстановления Intel](../../.github/workflows/hvf-intel-recovery.yml) собирает только `NeverDHvfTests` и запускает исходный фильтр `HvfExecutor.Native*` в одном процессе с `repetitions=100` или `1000`. Требуются точный `source-ref`, нативная проверка Intel VM/vCPU, Release, включённый HVF и отключённый Unicorn. Контроллер, проверяемые исходники и официальный загрузчик artifacts получают отдельные рабочие копии.

Action загружает план до начала исполнения. Во время исполнения сохраняются начальная отметка процесса, прогресс после не менее 25 дополнительных завершённых повторов и не более одного снимка остановившегося прогресса при наличии ещё не сохранённого нового вывода. Прогресс во время загрузки объединяется; допускается не более 42 artifacts прогресса и 1 MiB на копию журнала. Загружаются только зафиксированные каталоги. Загрузка не приостанавливает повторы и не сбрасывает таймеры, но влияет на планирование хоста; это частичные данные с инструментированием.

Успех требует последовательных итераций от 1 до запрошенного числа, парных записей RUN/OK/PASSED именно нужного нативного теста в каждой итерации, отсутствия ошибок и пропусков, нулевого кода выхода и подтверждённого завершения процесса. XML, перезаписываемый при повторах, этого не доказывает. Общий лимит нативного исполнения — три или десять минут, плюс 30 секунд на очистку контроллера; лимит action — 20 минут. Ошибка загрузки отменяет исполнение, а отмена завершает нативную группу процессов и загрузчик. Итоговые данные загружаются, если хост доступен. Неполные или усечённые снимки не удовлетворяют полной проверке CPU или Darwin.

`runner=hosted-intel` остаётся вариантом по умолчанию для workflow восстановления. `runner=self-hosted` использует существующие метки `[self-hosted, macOS, X64, hvf]` для сравнения хостов Intel. Оба варианта требуют нативного x86-64 и проверки VM/vCPU. На размещённых образах устанавливается Ninja; собственные хосты должны заранее предоставлять `cmake`, `ninja`, `python3`, `clang` и `codesign`. Изоляция исходников, ограничения повторов, проверка доказательств и обработка ошибок одинаковы. Нужен доступный runner с подходящими метками; оборудование автоматически не создаётся.

2026-10-03 чистый исходный код `e4a8169e69eb668ed3795efe4bd5f42cf4f287c2` прошёл локальную нативную проверку ARM64 Release с включённым HVF, отключённым Unicorn и `NEVERD_LLVM_PREBUILT=ON`. Полный профиль CPU сверил 20 целей, 520 методов и 7,125 результатов: 882 успешных, 6,243 пропущенных, ошибок нет; все 16 обязательных нативных случаев успешны. Независимый профиль Darwin сверил 32 метода и 286 результатов: 65 успешных, 221 пропущенный, ошибок нет; все 39 обязательных нативных случаев успешны. Исходный цикл восстановления в одном процессе также завершил 1,000 последовательных повторов, после чего прошли все 12 нативных транспортных случаев. Исходные журналы, XML, статусы процессов и соответствующие определения исходников проверены независимо. Итоги CPU и Darwin пересекаются, поэтому их нельзя складывать. Эти результаты не подтверждают полную проверку Intel или сборку с SDK iOS.

[Workflow в личном репозитории](https://github.com/gmh5225/test_mac_intel) позволяет проверять код на размещённом Intel runner без собственного Intel Mac. Ревизии диагностики и проверяемого кода фиксируются отдельно; ревизия workflow также записывается. Время ожидания и стабильность оцениваются независимо. До сообщения об ошибке диагностика сохраняет PID, родителя, исполняемый файл, код выхода, сигнал и причину завершения каждого процесса загрузки. После сбоя Action сборщик ждёт до 20 секунд и копирует только отчёты macOS IPS с совпадающими PID, родителем, именем процесса и временем выполнения. Отсутствие отчётов отмечается явно. Сбой загрузки по-прежнему останавливает нативный запуск, но сам по себе не доказывает сбой гипервизора или успешное прохождение теста.

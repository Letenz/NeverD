# Распаковка упакованных исполняемых файлов

`neverd unpack` восстанавливает программу, которую упакованный исполняемый файл заново собирает в собственном адресном пространстве. Команда запускает входной файл как ограниченный гостевой процесс, наблюдает, где загрузчик-заглушка передаёт управление созданному им коду, и записывает этот образ в новый файл того же контейнера. Девиртуализация не выполняется: функции, виртуализованные протектором, остаются виртуализованными. Сборка требует `NEVERD_ENABLE_CPU_EMULATION=ON`.

## Поддерживаемые входные файлы

Контейнер определяет, как файл проверяется и восстанавливается, набор инструкций определяет, как оценивается передача, а вместе они определяют профиль гостевого процесса. Входной файл вне этой таблицы отклоняется поимённо до выполнения чего-либо.

| Контейнер (`format`) | Набор инструкций | Гостевой профиль | Свидетельство входа |
| --- | --- | --- | --- |
| PE32+ (`pe64`) | x86-64 | [`windows-pe64-v1`](process-emulation.md) | наблюдение при выполнении |
| PE32+ (`pe64`) | ARM64 | [`windows-pe64-v1`](process-emulation.md) | наблюдение при выполнении |

DLL PE32+ определяются по `IMAGE_FILE_DLL`. Моделируемый гостевой EXE вызывает `LoadLibraryA`, затем `FreeLibrary` через обычный жизненный цикл зависимостей, TLS и `DllMain`. Вход DLL — её вызов присоединения к процессу; аргументы произвольных экспортов не выдумываются. Сохраняются имена, ординалы, псевдонимы, данные и перенаправления. Указатели на собственные экспорты остаются внутренними, без самоимпорта. Это относится и к адресам, возвращаемым вспомогательными функциями: внутренний результат отзывает прежние свидетельства исправления импортов для этого места.

## Использование

```bash
neverd unpack packed.exe -o unpacked.exe
neverd unpack packed.exe -o unpacked.exe \
  --options='{"backend":"unicorn","instruction_limit":400000000,"transfer":2}'
```

Команда выводит один отчёт JSON. Код завершения 0 означает, что образ записан, 3 — что ограниченное выполнение закончилось раньше, чем была принята точка входа (`outcome` равно `no_entry`, и ничего не записывается), 1 — недопустимый входной файл, параметр или сбой подготовки. В отчёте указаны фактически использованные `format`, `architecture` и `profile`. Точка входа C — `neverd_unpack_json`; в Python доступен `Session.unpack`. Параметры — это [параметры процесса](process-emulation.md) плюс `transfer`. Значения по умолчанию отличаются там, где заглушке нужно больше ресурсов: 100000000 инструкций, 600 секунд и 512 MiB, а `windows.defer_unmodeled` включён.

## Как определяется точка входа

Нулевое поколение — входной образ при отображении гостевым загрузчиком. Передача начинает более новый код. `transfers` содержит RVA, `generation`, равенство стека (`stack_balanced`) и принадлежность входному вызову образа (`program_invocation`). Для DLL это присоединение к процессу. До него базой служит стек первого инициализатора.

1. Вход по умолчанию требует одновременно `stack_balanced` и `program_invocation`: заглушка вернула стек входного вызова. `entry_source` равен `transfer`.
2. TLS-callbacks ОС, входы зависимых DLL и вызовы отсоединения не становятся входом по умолчанию даже при равном стеке. Более глубокие гостевые вызовы продолжаются. Callbacks не пропускаются, сигнатуры заглушки не предсказывают вход.
3. `transfer` явно выбирает позицию списка, включая callbacks инициализации и промежуточные этапы.

Точка входа не предсказывается по виду стартового кода компилятора. Выполнение, остановившееся раньше, сообщает `no_entry` и `stop_reason` процесса.

Выполненная страница 4 KiB остаётся наблюдаемой. Зафиксированные записи гостевой RAM инвалидируют посещённые страницы через физические алиасы; модель процесса перепроверяет их и после служб ОС перед возобновлением. Свидетельство передачи сравнивает фактическую длину инструкции из декодера CPU: изменения соседних данных сами по себе не устанавливают вход. Смешанные поколения и повторные изменения остаются под наблюдением, включая callbacks, возвращающиеся к старому stub на той же странице.

## Восстановленный образ

Секции сохраняют RVA, наблюдавшуюся память (включая эффекты уже выполненной инициализации) и права страниц. Новая секция `.neverd` содержит каталог импортов и новые ячейки IAT для вызовов экспортов и загрузок адресов, сохраняя исходные нулевые области. `origin` в `imports` различает ячейки `static`, связанные из входного файла, и `runtime`, записанные гостем либо добавленные при исправлении. Перемещения сгенерированных данных не наблюдались, поэтому образ фиксируется по наблюдавшейся базе, каталог перемещений удаляется и устанавливается `IMAGE_FILE_RELOCS_STRIPPED`.

Перезапись файловых смещений отладочных данных требует полного файлового покрытия каталога отладки и каждого сохраняемого блока данных.

Записываемым ячейкам импорта не нужен собственный диапазон защиты IAT; их дескрипторы по-прежнему связывают каждую ячейку. Для ячеек только для чтения требуется непрерывный диапазон секций, доступных только для чтения и не допускающих выполнение. Диапазон, пересекающий записываемые или исполняемые секции, вызывает явную ошибку вместо изменения защиты памяти.

Существующие кандидаты IAT должны образовывать непрерывный массив указателей на экспорты одного поставщика с целым нулевым завершителем внутри исходной секции. Завершитель соседнего поставщика не подходит.

Исходный каталог TLS, соответствующий идентичности выделения загрузчика, может не иметь массива callbacks или иметь пустой массив. Найденные сканированием заменяющие записи по-прежнему требуют полного списка с нулевым завершителем и свидетельства выполнения callbacks. Несколько кандидатов вызывают явную ошибку. Имена и байты конкретных протекторов не используются. При выборе каталога наблюдаемое выполнение сгенерированных callback имеет приоритет перед завершённым инициализатором загрузчика. Повторный вызов программой уже завершённого инициализатора загрузчика остаётся резервным свидетельством, даже если код этого инициализатора был изменён.

`materialized_tls_callbacks` считает TLS-callbacks присоединения входного образа, вернувшиеся до снимка. Доказательство требует записи вызова ОС либо наблюдаемого входа в сгенерированный код с `(image_base, 1, 0)`, после которого достигнут адрес возврата ABI с восстановленным указателем стека. Их изменения памяти уже есть в снимке. Адаптеры новой секции `.neverd` обходят только этот повторный вызов, а другие уведомления передают исходному callback хвостовым вызовом. Каталог, таблица и адаптеры используют новую память; исходные байты сохраняются. Секция исполняемая при наличии адаптеров и записываемая только при необходимости новых ячеек IAT. Внутренние гостевые callbacks без такого свидетельства завершения сохраняют поведение. При присоединении процесса адаптер восстанавливает захваченные TLS-байты главного потока, отличающиеся от шаблона, даже если ни один callback не завершён. Отсутствие снимка TLS или несовпадение размера вызывает явную ошибку. Исходный шаблон сохраняется для будущих потоков; другие уведомления не восстанавливают захваченный блок.

Отложенная загрузка допускает исполняемые цели callbacks и входа в изначально нулевой памяти, код которой создают предыдущие инициализаторы. Массивы callbacks и метаданные выделения TLS по-прежнему требуют проверенных файловых данных; строгая загрузка сохраняет проверки. Модель ОС сообщает принадлежность вызова и уведомляет наблюдателя при подготовке вызова или восстановлении приостановленного вызывающего кода. На этих границах наблюдение за передачами включается заново, в том числе когда callback и созданный вход находятся на одной странице.

`import_repair` охватывает два дополнительных ограниченных запуска после захвата входа: поиск вызовов экспортов и наблюдение состояния подпрограмм. Каждый запуск имеет отдельные лимиты процесса. Счётчики инструкций и событий складываются с насыщением; `stop_reason` и диагностика относятся к последнему запуску, число вызовов — только к поиску. Без адресов продолжения наблюдение пропускается. Противоречивые идентификаторы экспортов запрещают изменение. Покрыты лишь достигнутые пути; `unpacked` не удостоверяет все импорты или успешное выполнение программы.

Порядок связывания импортов может менять адреса экспортов. Исправление сохраняет идентичность из проверяющего запуска и наблюдает экспорты, разрешённые после входа; адрес из другого запуска не разрешает перезапись.

Поиск наблюдает диспетчеризацию экспортов, включая немоделируемый экспорт, останавливающий выполнение, а не только журнал моделируемых вызовов. Нечитаемое место возврата ABI не может служить доказательством подпрограммы. Исправление чистого вызова непрозрачного экспорта сохраняет явную остановку неподдерживаемой службы.

Наблюдаются не более 256 начал-кандидатов в 256 байтах перед фактическими продолжениями вызовов экспортов. `CALL rel32`, возможно после PUSH/POP GPR, задаёт лишь границу наблюдения; следующие байты не являются сигнатурой. Окно вызова в шесть-восемь байт заменяется на `call [rip+IAT]`, только если при входе API добавлен ровно один адрес возврата, другие регистры (включая флаги и SIMD), отображения и постоянная RAM неизменны, без промежуточных вызовов ОС. Начальные NOP сохраняют точный адрес возврата. Семь-восемь байт заменяются на `mov r64, [rip+IAT]`, если известный экспорт возвращён в одном GPR при сбалансированном стеке и тех же условиях сохранения. Регистр результата определяется сравнением состояний: любой GPR кроме RSP, включая R8-R15; восьмибайтная загрузка оставляет NOP в конце. Исключается лишь временная область ниже SP вызывающего; его стек сравнивается. Последующий нечистый, неразрешённый или незавершённый вызов отменяет доказательство. Требуется фактическое начало; предыдущий байт не разрешает REX, перекрывающиеся начала с общим возвратом отвергаются. `observed_loads` и `repaired_loads` отдельно считают загрузки адресов.

`ImportObserver` сохраняет один внешний снимок при промежуточных остановках исполнения. Вложенный кандидат теряет прежние доказательства, поскольку отдельного снимка для него нет. Внешний вызов по-прежнему требует полного сравнения регистров, отображений памяти, постоянной памяти и вызовов ОС. Рекурсивные, прерванные и незавершённые вызовы теряют свои доказательства. `ProcessImportsTests.cpp` и независимо скомпонованная тестовая DLL проверяют эти границы. Только кандидат с наблюдаемой точкой продолжения экспортного вызова сохраняет снимок при вложенных остановках.

Исходная таблица секций, расположение каталога импорта и таблица перемещений не восстанавливаются: упаковщик не воссоздаёт их в памяти.

## Распознавание

Совместимые поля `packer.kind` и `packer.evidence` возвращают `unidentified` и пустой массив. Реестр протекторов, анализ заголовков упаковки и сигнатуры заглушек удалены. Прежний API только проверяет контейнер.

## Ограничения

Проверяемое выполнение идёт по инструкциям. x64 Unicorn/KVM/WHP также поддерживает `direct-user-x64-v1` с ограничением времени и событий без подсчёта инструкций. Смешанные поколения и повторные записи могут требовать дополнительных шагов процессора. Восстановление охватывает достигнутые пути основного образа; созданный вне него код не становится его входом. Инициализация до входа может создать непереносимое внешнее состояние, а повтор TLS callbacks — дополнительные эффекты. Немоделируемые API явно останавливают выполнение. Исправляются проверенные окна вызовов x64 в шесть-восемь байт и загрузки адресов в семь-восемь байт; другие формы и недостигнутые пути остаются неразрешёнными. Виртуализированный код остаётся таким.

## Проверка

`NeverDUnpackTests` проверяет контейнеры, безопасное выделение IAT, конфликты и отказ TLS. `NeverDUnpackExecutionTests` проверяет UPX NRV2B/NRV2D/NRV2E/LZMA и CRT общим путём на Unicorn/KVM/WHP, сравнивает секции с независимо скомпонованной программой после её собственной инициализации и требует одинаковых результатов доступных backend. `UnpackGeneratedTests.cpp` создаёт независимые программы x86-64/ARM64 для передач, поэтапной загрузки, импортов и прямого выполнения x64 Unicorn/KVM/WHP. Обязательные нативные случаи CI нельзя пропускать. `NeverDUnpackPublicTests` покрывает C ABI и CLI. `unittests/unpack/fixtures/Makefile` пересоздаёт образцы UPX.


`UnpackLibraryTests.cpp` упаковывает независимые x64/ARM64 DLL внутри теста и проверяет порядок зависимостей, обычные/сгенерированные TLS-callbacks, очистку при отказе, идентичность входа/хоста, доступ к своему файлу, имена/ординалы/данные/перенаправления и отсутствие самоимпорта. Нативная Windows загружает исходные и восстановленные DLL отдельным EXE и вызывает объявленные экспорты; проверяемые и прямые WHP-тесты обязательны. `CompletedGeneratedTLSCallsRequireTheAttachABI` отвергает изменённые вход/аргументы; `GeneratedCallsNeedTheirReturnedStackAtTheContinuation` отвергает неверный стек возврата. Проверяется распаковка без девиртуализации.

`ExportObserver` также наблюдает исполняемые экспорты резидентных гостевых зависимостей; моделируемые поставщики наблюдаются при диспетчеризации служб. Собственные экспорты входа исключены. Изменения модулей обновляют остановки, а каждая правка требует текущей идентичности экспорта. Записи ограничены объявленным пределом импортов. DLL-тесты исправляют помощники системных API и зависимостей; нативная загрузка проверяет отсутствие остаточных эмулированных адресов.


`WrappedEntriesRequireExplicitTransferEvidence` проверяет DLL-обёртку, вызывающую восстановленный вход на более глубоком стеке. По умолчанию остаётся `no_entry`; выбор наблюдаемого вызова через `transfer` создаёт загружаемую DLL. Глубина вызова сама по себе не отличает вход от инициализатора.

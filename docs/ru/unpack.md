# Распаковка упакованных исполняемых файлов

`neverd unpack` восстанавливает программу, которую упакованный исполняемый файл заново собирает в собственном адресном пространстве. Команда запускает входной файл как ограниченный гостевой процесс, наблюдает, где загрузчик-заглушка передаёт управление созданному им коду, и записывает этот образ в новый файл того же контейнера. Девиртуализация не выполняется: функции, виртуализованные протектором, остаются виртуализованными. Сборка требует `NEVERD_ENABLE_CPU_EMULATION=ON`.

## Поддерживаемые входные файлы

Контейнер определяет, как файл проверяется и восстанавливается, набор инструкций определяет, как оценивается передача, а вместе они определяют профиль гостевого процесса. Входной файл вне этой таблицы отклоняется поимённо до выполнения чего-либо.

| Контейнер (`format`) | Набор инструкций | Гостевой профиль | Знание о заглушке |
| --- | --- | --- | --- |
| PE32+ (`pe64`) | x86-64 | [`windows-pe64-v1`](process-emulation.md) | UPX |
| PE32+ (`pe64`) | ARM64 | [`windows-pe64-v1`](process-emulation.md) | нет; только наблюдение |

## Использование

```bash
neverd unpack packed.exe -o unpacked.exe
neverd unpack packed.exe -o unpacked.exe \
  --options='{"backend":"unicorn","instruction_limit":400000000,"transfer":2}'
```

Команда выводит один отчёт JSON. Код завершения 0 означает, что образ записан, 3 — что ограниченное выполнение закончилось раньше, чем была принята точка входа (`outcome` равно `no_entry`, и ничего не записывается), 1 — недопустимый входной файл, параметр или сбой подготовки. В отчёте указаны фактически использованные `format`, `architecture` и `profile`. Точка входа C — `neverd_unpack_json`; в Python доступен `Session.unpack`. Параметры — это [параметры процесса](process-emulation.md) плюс `transfer`. Значения по умолчанию отличаются там, где заглушке нужно больше ресурсов: 100000000 инструкций, 600 секунд и 512 MiB, а `windows.defer_unmodeled` включён.

## Как определяется точка входа

Нулевое поколение — это образ в том виде, в каком его отобразил гостевой загрузчик. Инструкция, байты которой отличаются от этого образа, создана самим процессом. Передача — это первое выполнение кода, более нового, чем выполнявшийся; `transfers` перечисляет каждую передачу с её RVA, `generation` и признаком того, равен ли указатель стека своему значению при входе в процесс (`stack_balanced`).

1. Передача на входном стеке — это точка входа программы: заглушка вернула полученный стек. `entry_source` равно `transfer`.
2. Передача на более глубоком стеке — это вызов программы заглушкой, например обратный вызов TLS. Он отражается в отчёте, но не принимается. Если распознанная заглушка называет цель своего последнего перехода, образ восстанавливается в момент этого вызова, до выполнения какого-либо кода программы, а названный адрес становится точкой входа. `entry_source` равно `stub`.
3. `transfer` явно выбирает передачу из списка по её номеру — для протекторов, которые распаковывают поэтапно или вызывают свою программу.

Точка входа не предсказывается по виду стартового кода компилятора. Выполнение, остановившееся раньше, сообщает `no_entry` и `stop_reason` процесса.

## Восстановленный образ

Секции сохраняют свои RVA и содержат наблюдавшуюся память; у каждой секции те права доступа, которые были у её страниц в момент передачи. Последняя секция `.neverd` содержит новый каталог импорта поверх ячеек, через которые программа уже выполняет вызовы, поэтому ни код, ни данные не перемещаются. `imports` перечисляет каждую ячейку с её `origin`: ячейки `static` связаны загрузчиком по каталогу самого входного файла, ячейки `runtime` записаны заглушкой. Образ закреплён на наблюдавшейся базе: перемещения сгенерированного содержимого не наблюдались, поэтому каталог перемещений удаляется и устанавливается `IMAGE_FILE_RELOCS_STRIPPED`. Для UPX заново указывается собственный каталог TLS программы, потому что упакованный ведёт только к обработчику заглушки.

Исходная таблица секций, расположение каталога импорта и таблица перемещений не восстанавливаются: упаковщик не воссоздаёт их в памяти.

## Распознавание

`packer.kind` называет протектор только на основании свидетельств в файле. Для UPX нужны два из трёх: `upx_section_names`, `upx_pack_header` (сигнатура, формат, метод и контрольная сумма) и `upx_entry_stub`. Нераспознанный входной файл всё равно распаковывается наблюдением.

## Ограничения

Поддерживаются только исполняемые файлы; DLL не запускаются. Проверяемое выполнение допускает по одной инструкции за раз, порядка 10^5 в секунду, поэтому заглушка, которой нужны миллиарды инструкций, превышает любой практический бюджет. Выполнение отслеживается по страницам размером 4 KiB: код, записанный в страницу, где уже выполняется код того же поколения, не сообщается как передача. Код программы, выполняющийся до точки входа, например обратный вызов TLS, обращающийся к немоделируемому API, останавливает выполнение, если только заглушка не объявляет свою точку входа. Загрузчик VMProtect распаковывается, когда каждый защищённый вызов импорта остаётся участком в шесть байт, который хвостовым вызовом входит в уже разрешённый экспорт. Эти участки переписываются как обычные вызовы импорта. Виртуализированный код остаётся виртуализированным.

## Проверка

`NeverDUnpackTests` проверяет распознавание. `NeverDUnpackExecutionTests` распаковывает хранящиеся в репозитории образцы UPX (NRV2B, NRV2D, NRV2E, LZMA и программу с библиотекой времени выполнения C) на Unicorn, KVM и WHP, сравнивает каждую секцию с оригиналом, запускает восстановленный образ и требует от всех бэкендов одинаковых байтов. `UnpackGeneratedTests.cpp` упаковывает программу внутри теста для x86-64 и ARM64 и сверяет со скомпонованным файлом три загрузчика: уходящий сразу, сначала вызывающий программу и двухступенчатый. `NeverDUnpackPublicTests` охватывает C ABI и CLI. `unittests/unpack/fixtures/Makefile` заново создаёт образцы UPX.

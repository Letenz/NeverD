# Выполнение CPU и запросы возможностей

Выполнение CPU не зависит от гостевой ОС, загрузчика образов и соглашения о вызовах. `NEVERD_ENABLE_CPU_EMULATION` включает его отдельную сборку, а `NEVERD_ENABLE_DRIVER_EMULATION` дополнительно включает модель драйверов Windows. [Руководство по архитектуре](architecture.md) описывает владение, выбор бэкенда и текущие ограничения платформ.

## Конфигурация

Публичная [`ExecutionConfiguration`](../../include/neverd/emulation/ExecutionConfiguration.h) используется и фабрикой CPU, и отчётом о возможностях. Требования проверяются до выделения CPU или подключения адресного пространства. Пропущенные значения задаются фиксированным профилем контракта; явно заданные неподдерживаемые значения приводят к ошибке.

| Поле JSON | По умолчанию | Значение |
|---|---|---|
| `backend` | `auto` | `auto`, `unicorn`, `kvm` или `whp` |
| `contract` | `software-cpu-v1` | Версионированная семантика выполнения |
| `architecture` | `x86_64` | `x86_64` или `aarch64` |
| `privilege` | Профиль контракта | `flat`, `supervisor` или `user`; должен соответствовать контракту |
| `virtual_address_bits` | Профиль контракта | Проверенные профили: 48 бит; плоские: прямое пространство отображения 64 бит |
| `page_size` | 4096 | Гранула отображения гостя; другие значения отклоняются |
| `required_features` | `[]` | Имена функций из [`ExecutionConfiguration.def`](../../include/neverd/emulation/ExecutionConfiguration.def) |

`driver-strict` принимает x64, `software-cpu-v1` — x64 и ARM64. `checked-x64-v1` и `checked-aarch64-v1` требуют указанную архитектуру и режим supervisor. `checked-user-x64-v1` и `checked-user-aarch64-v1` исполняют соответствующий контракту ограниченный набор инструкций при CPL3 и EL0 с изоляцией MMU и явными выходами запросов служб. Поддерживаются Unicorn и соответствующий хосту KVM/WHP; `auto` следует выбору хоста. Плоские профили не гарантируют архитектурную изоляцию user/supervisor. Проверенный ARM64-профиль отклоняет FP/SIMD, а x64 допускает ограниченные семейства ниже. Supervisor-x64 дополнительно поддерживает ограниченные MMIO-транзакции и подготовленные строковые чтения; user-профили отклоняют отображение устройств. Портовый ввод-вывод и параллельные CPU остаются запрещены во всех проверенных профилях. Только user-профили объявляют `service_traps`.

Для пользовательского исполнения каждой отображённой странице нужны `UserAccessible` и соответствующее право `Read`, `Write` или `Execute`. Существующие отображения по умолчанию доступны supervisor; у псевдонимов независимые права даже при общих физических байтах. `UserAccessible` само по себе доступа не даёт. Доверенные операции хоста и supervisor-CPU используют RWX. Пример:

```cpp
Configuration.Contract = ExecutionContract::CheckedUserX64;
Configuration.Privilege = ExecutionPrivilege::User;
auto CPU = llvm::cantFail(createExecutionBackend(Configuration, Space)).CPU;
llvm::cantFail(CPU->map(Code, 4096, Read | Write | Execute | UserAccessible));
```

Привилегия фиксируется контрактом; восстановление контекста и привязка адресного пространства её не меняют, а x64-селекторы сегментов не могут её повысить. Восстановимая ошибка доступа к данным сохраняет исходную инструкцию и регистры до обработки владельцем. `canAccess` проверяет ровно запрошенные права; для проверки пользовательской видимости добавьте `UserAccessible`. Таблицы страниц — частные проекции CPU: изменяемые гостевые таблицы и API смены привилегий не предоставляются. В ARM64 пользовательские страницы также не исполняются на EL1.

Неизвестные/null-поля, недопустимые имена или числовые ширины, повторные обязательные функции и неподдерживаемые комбинации приводят к ошибке. Ввод ограничен 64 KiB; старые фабрики CPU и C-параметры драйверов остаются совместимыми.

## Запрос без выполнения рабочей нагрузки

```bash
neverd cpu-capabilities
neverd cpu-capabilities \
  --configuration='{"contract":"checked-aarch64-v1","architecture":"aarch64"}' \
  --probe-host
```

Версия схемы — 1. Отчёт разделяет `requested_configuration` до подстановки профиля, нормализованную `configuration`, статические семантические `capabilities`, сборочную поддержку адаптера/ABI в `build` и `host` (null без `--probe-host`). Проверка хоста инициализирует временный CPU на частной RAM и подтверждает только возможность инициализации, но не пригодность рабочей нагрузки или нативное исполнение ARM64. Доступность может измениться; недоступный бэкенд никогда не выбирается молча вместо запрошенного. CLI возвращает 0 для корректного отчёта, даже если бэкенд недоступен, и 1 при неверной конфигурации/запросе.

## Границы SDK и C++

[`neverd_cpu_capabilities_json`](../../include/neverd/sdk/NeverDCAPICPU.h) принимает существующую сессию, необязательный JSON конфигурации и `ProbeHost` со значением 0 или 1; загруженный образ не нужен. Освободите результат через `neverd_free_string`; NULL означает ошибку, подробности доступны в `neverd_last_error`. Сборки без CPU экспортируют ту же функцию и явно сообщают об отключённой функции. Python-плагины вызывают `session.cpu_capabilities(...)`. В C++ функции `executionCapabilities`, `resolveExecutionConfiguration`, `queryExecutionBackendBuild` и `probeExecutionBackend` доступны раздельно; `createExecutionBackend` подключает CPU к существующему пространству либо создаёт частную RAM и пространство по умолчанию.

## Результаты CPU и бюджеты

`CPU.runUntilExit(PC, TimeoutMicroseconds)` возвращает типизированный [`ExecutionExit`](../../include/neverd/emulation/ExecutionExit.h). Ошибки настройки возвращаются как `llvm::Error`; начатое выполнение сообщает явную остановку, deadline, запрос службы, восстановимую ошибку, гостевую ошибку/trap, неподдерживаемую операцию, сбой устройства/бэкенда или необъяснимую остановку движка. Ошибки CPU/устройства/бэкенда имеют приоритет над одновременной остановкой или deadline, а независимые факты и подробности сохраняются. Тайм-аут должен быть положительным и представимым как длительность и абсолютный deadline; иначе вызов завершается до изменения CPU. Каждому запуску нужен конечный бюджет; ноль не означает ни бесконечное выполнение, ни допустимый немедленный тайм-аут. Контроль кооперативный, жёсткая граница реального времени не обещается. Результат не потребляет восстановимую ошибку: владелец ОС должен получить её и установить проверенный переход исключения до возобновления. Старые `run`, `fault` и `timedOut` остаются; внешние реализации CPU, переопределяющие только `run`, отклоняют новую типизированную границу.

## Запросы служб

Профиль user-x64 перехватывает только точную инструкцию `SYSCALL` без префикса; user-ARM64 — `SVC #imm16`. `SYSENTER`, `INT`, `HVC`, `BRK` и другие механизмы не поддерживаются. Сначала запускается наблюдатель инструкций. Если он не остановил CPU и не сообщил ошибку, CPU возвращает `ExecutionExitKind::ServiceRequest` **до** исполнения инструкции или входа в бэкенд, указывая тип, исходный `PC`, последовательный `NextPC` и immediate SVC. Регистры, флаги, стек и привилегия не меняются: x64-изменения RCX/R11 от SYSCALL ещё не произошли, ARM64 не вошёл в вектор исключения. Immediate SVC не является универсальным номером службы.

Запрос остаётся ожидающим и блокирует выполнение, изменение CPU, привязку адресного пространства и сохранение/восстановление контекста, пока владелец ОС ровно один раз не получит его через `takeServiceRequest()` на остановленном CPU. Владелец декодирует ABI ОС, обрабатывает службу и явно задаёт регистры результата и следующий PC/переход исключения. Неподдерживаемая служба завершается ошибкой на этой границе; повторный запуск исходного PC создаёт новый запрос, но не подставляет NOP или успешный результат. Событие службы приоритетнее одновременной остановки/deadline, но гостевые ошибки и ошибки бэкенда выше него. Остановка CPU, программный HLT, deadline или trap не доказывают успешное завершение нагрузки. Отдельный [профиль Linux-процесса](process-emulation.md) использует собственную модель ОС и не подтверждает работу Windows, Android или Darwin. Нативное исполнение на Windows и ARM64 требует отдельной проверки во время выполнения.

## Расширения x64 и нативное состояние CPU

Проверенный x64 допускает ограниченные legacy-перемещения и логические операции SSE/SSE2, `MOVLHPS`/`MOVHLPS` и маскированные скалярные формы `CVTTSS2SI`/`CVTTSD2SI`/`SUBSS`/`SUBSD`. MXCSR сохраняет sticky-статус, округление и FTZ; DAZ и немаскированные исключения отклоняются. Проверенный ARM64 по-прежнему отклоняет FP/SIMD. KVM/WHP синхронизируют все 16 XMM-регистров и MXCSR; не перечисленные кодировки и операнды остаются запрещены.

Проверенный x64 также допускает маскированные legacy-формы `SS`, `SD`, `PS`, `PD` инструкций `ADD`, `SUB`, `MUL`, `DIV`, `SQRT`, `MIN`, `MAX`. `X64SSEInstructions.def` централизует ширины, выравнивание и допуск. `MaskedSSEArithmeticMatchesIndependentHostExecution` сравнивает регистры/RAM с независимым эталоном CPU хоста: четыре режима округления, FTZ, знаковые нули, субнормальные числа и NaN. `SSEMemoryObserverStopsBeforeResultAndStatusChanges` проверяет остановку до эффектов. DAZ, немаскированные исключения, x87 и AVX остаются исключёнными.

Указатель потока охватывает FS/GS в x64 и `TPIDR_EL0` в ARM64 с точными кодировками `MRS`/`MSR`. Нативные транспорты и снимки CPU сохраняют это состояние отдельно от памяти, но не создают потоки ОС или блоки TLS. Supervisor-x64 допускает выровненные скалярные MMIO-транзакции 1/2/4 байта и один элемент MOVS на границу возобновления. Чтение устройства требует чистого подготовленного просмотра и не более одного commit. User-профили запрещают отображение устройств; RMW, широкое MMIO и портовый I/O также не поддерживаются.

KVM/WHP отменяют активные нативные входы и подтверждают отмену до освобождения ресурсов выполнения. KVM использует отдельный поток и временно разблокирует realtime-сигнал; выбранный сигнал не должен игнорироваться во время входа. Маски сигналов и обработчики вызывающего процесса не меняются. При неопределённом прогрессе гостя отмена становится терминальной ошибкой; жёсткий wall-clock deadline не гарантирован.

## Нативные синхронные исключения x64

Checked x64 выполняет `DIV`/`IDIV` с реальными результатами процессора и `#DE`. KVM использует закрытые supervisor IDT/IST, WHP — явную маску исключений; исходный контекст и доступные коды отделены от ошибок транспорта. ОС получает восстанавливаемое событие перед установкой продолжения. Windows-драйверы преобразуют деление на ноль и переполнение частного в `STATUS_INTEGER_DIVIDE_BY_ZERO`, выполняя настоящие SEH-фильтры, `__finally` и повтор инструкции. `NeverDX64ExceptionTests` собирается без Unicorn; `DriverWDMCPUException` проверяет исходные WDK-примеры. Недоступные WHP/ARM64-хосты явно пропускаются.

## Подготовленные эффекты RAM

`RAMTransaction` сохраняет только физическое объединение заявленных диапазонов записи инструкции под блокировкой выполнения. До вызова наблюдателей результата исходная RAM восстанавливается; отмена, ошибка транспорта или исключение наблюдателя не публикуют частичные изменения RAM и регистров. После отката RAM ошибки CPU сохраняют архитектурное состояние исключения. Одиночные и парные записи ARM64 используют тот же механизм. x64 выполняет `XCHG`, `XADD` и `CMPXCHG` шириной 8/16/32/64 бит; формы с LOCK или неявной блокировкой требуют естественного выравнивания. `NeverDRAMTransactionTests` сравнивает результаты с CPU хоста и проверяет откат, алиасы и права; недоступные платформы явно пропускаются. Устройства и параллельный SMP не входят в контракт. Снимки CPU не откатывают уже подтверждённую RAM.

## Полное состояние x87

`NeverDEmulationArch` владеет контрактами ISA, таблицами страниц и форматом FP, общим для нативных транспортов и Unicorn. Контексты x64 сохраняют управление, статус, TOP, физические теги, код операции, указатели инструкций/данных и восемь 80-битных регистров. `FP0`–`FP7` используют `RegisterValue`; скалярный доступ отвергает усечение. `FPTag` — физическая маска непустых регистров. `NeverDX64FPTests` проверяет все TOP, точные операции по FXSAVE/FXRSTOR хоста и восстановление. Это не разрешает инструкции x87 в checked и не доказывает всю семантику округления. Недоступные нативные хосты явно пропускаются.

`driver-strict` поддерживает KVM на совместимых хостах Linux x64 и WHP на Windows x64; `auto` выбирает этот нативный транспорт, а другая ISA использует Unicorn. Явный Unicorn и прежний API V1 сохраняют переносимый программный профиль. Нативное выполнение проверяет канонические адреса и эффекты до входа; недоступное оборудование вызывает ошибку без подмены. Неподдерживаемые инструкции и поведение OS завершаются явной ошибкой. Нативные свидетельства ARM64/WHP ещё отсутствуют; совместимость произвольных драйверов или Android/Darwin не установлена.

Выбранный профиль можно запросить через `executionCapabilities(Contract, ISA, Backend)`. `NativeLegacyX64` описывает нативное выполнение драйверов x64. `NeverDNativeDriverTests` проверяет существующий набор драйверов и работает также в сборке без Unicorn.

KVM x64 использует `KvmRunControl` для подготовки состояния, входа в `KVM_RUN` и чтения состояния в одном выделенном потоке vCPU. Подготовка выполняется один раз до повторов после `EINTR`; чтение выполняется только после успешного возврата из входа на хосте. Заимствованные функции передачи действуют до подтверждения завершения входа. Декодирование ISA, транзакции RAM, политика ОС и наблюдатели исполнения остаются в вызывающем потоке. Ошибка подготовки исключает вход и чтение; ошибка чтения или отмена запрещает публикацию состояния гостя.

KVM сравнивает общие регистры и полное состояние FP/SSE с последним подтверждённым чтением после отладки по `X64HostRegisters.def` и `X64FPState.def`, повторно задавая изменённые входные данные. Записи хоста и восстановление контекста также сравниваются; исключения, отмена и ошибки запрещают повторное использование. Пошаговый режим и чтение реального общего/FP-состояния сохраняются для каждой инструкции.

Аппаратное исполнение само по себе не гарантирует меньшую общую задержку. Текущее нативное исполнение выполняет допуск, наблюдение, передачу состояния и выход VM для каждой инструкции. Сравнивайте те же исходные образы и сценарии с одинаковыми бюджетами инструкций и событий, указывая совпадение результатов вместе со временем; при измерении задержки CLI учитывайте запуск и загрузку.

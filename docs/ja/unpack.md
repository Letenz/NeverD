# パックされた実行ファイルのアンパック

`neverd unpack` は、パックされた実行ファイルが自身のアドレス空間内に再構築するプログラムを復元します。入力を有界なゲストプロセスとして実行し、スタブが自ら生成したコードへ制御を渡す箇所を観測して、その時点のイメージを同じコンテナ形式の新しいファイルとして書き出します。仮想化の解除は行いません。保護ツールが仮想化した関数は仮想化されたままです。ビルドには `NEVERD_ENABLE_CPU_EMULATION=ON` が必要です。

## 対応する入力

コンテナ形式はファイルの検証と再構築の方法を、命令セットは転送の判定方法を決め、両者がゲストプロセスのプロファイルを決めます。この表にない入力は、何も実行される前に名前を挙げて拒否されます。

| コンテナ (`format`) | 命令セット | ゲストプロファイル | スタブの知識 |
| --- | --- | --- | --- |
| PE32+ (`pe64`) | x86-64 | [`windows-pe64-v1`](process-emulation.md) | UPX |
| PE32+ (`pe64`) | ARM64 | [`windows-pe64-v1`](process-emulation.md) | なし（観測のみ） |

## 使い方

```bash
neverd unpack packed.exe -o unpacked.exe
neverd unpack packed.exe -o unpacked.exe \
  --options='{"backend":"unicorn","instruction_limit":400000000,"transfer":2}'
```

コマンドは JSON レポートを 1 つ出力します。終了コード 0 はイメージが書き出されたこと、3 はエントリが受理される前に有界な実行が終了したこと（`outcome` は `no_entry` で、何も書き出されません）、1 は入力・オプションの不正または準備の失敗を表します。レポートには、実際に実行された `format`、`architecture`、`profile` が記載されます。C のエントリポイントは `neverd_unpack_json`、Python では `Session.unpack` です。オプションは[プロセスオプション](process-emulation.md)に `transfer` を加えたものです。スタブがより多くの資源を必要とする項目では既定値が異なります。100000000 命令、600 秒、512 MiB で、`windows.defer_unmodeled` は有効です。

## エントリの確定方法

第 0 世代は、ゲストローダーがマップした時点のイメージです。そのイメージとバイトが異なる命令は、プロセス自身が生成したものです。転送とは、実行中のコードより新しいコードが初めて実行されることです。`transfers` には各転送の RVA、`generation`、およびスタックポインタがプロセス開始時の値と等しいかどうか（`stack_balanced`）が列挙されます。

1. エントリ時のスタック上で起きた転送がプログラムのエントリです。スタブは与えられたスタックを返し終えています。このとき `entry_source` は `transfer` です。
2. より深いスタック上で起きた転送は、TLS コールバックのようにスタブがプログラムを呼び出したものです。これは報告されますが、受理されません。識別済みのスタブが最終ジャンプ先を示している場合、イメージはその呼び出しの時点（プログラムのコードがまだ一切実行されていない時点）で再構築され、示されたアドレスがエントリになります。このとき `entry_source` は `stub` です。
3. `transfer` は列挙された転送を位置で明示的に選択します。段階的に展開する保護ツールや、プログラムを呼び出す形で入る保護ツールのためのものです。

コンパイラのスタートアップコードの形からエントリを推測することはありません。先に実行が停止した場合は、`no_entry` とプロセスの `stop_reason` が報告されます。

## 再構築されたイメージ

各セクションは RVA を保ち、観測されたメモリを保持します。各セクションのアクセス権は、転送時点でそのページが持っていたものです。末尾の `.neverd` セクションには、プログラムがもともと経由して呼び出しているセルの上に新しいインポートディレクトリが置かれるため、コードもデータも移動しません。`imports` には各セルとその `origin` が列挙されます。`static` のセルはローダーが入力自身のディレクトリから束縛したもの、`runtime` のセルはスタブが書き込んだものです。イメージは観測されたベースに固定されます。生成された内容に対する再配置は観測されていないため、再配置ディレクトリは取り除かれ、`IMAGE_FILE_RELOCS_STRIPPED` が設定されます。UPX では、パック後のディレクトリがスタブのハンドラにしか届かないため、プログラム自身の TLS ディレクトリを指し直します。

元のセクションテーブル、インポートディレクトリの配置、再配置テーブルは再構築されません。パッカーはそれらをメモリ上に復元しないためです。

## 識別

`packer.kind` は、ファイル内の証拠だけに基づいて保護ツールを名指しします。UPX には `upx_section_names`、`upx_pack_header`（マジック、形式、方式、チェックサム）、`upx_entry_stub` のうち 2 つが必要です。識別できない入力も、観測によってアンパックされます。

## 制限

対応するのは実行ファイルのみで、DLL は実行されません。検査付き実行は一度に 1 命令ずつ受理し、毎秒 10^5 命令程度であるため、数十億命令を必要とするスタブは現実的な予算を超えます。実行は 4 KiB ページ単位で追跡されます。同じ世代のコードがすでに実行中のページへ書き込まれたコードは、転送として報告されません。エントリより前に動くプログラムのコード（未モデルの API を呼ぶ TLS コールバックなど）は、スタブがエントリを宣言していない限り実行を停止させます。保護されたインポート呼び出しが、解決済みのエクスポートへ末尾呼び出しする 6 バイトの箇所のままなら、VMProtect のローダーはアンパックされます。それらの箇所は通常のインポート呼び出しに書き換えられます。仮想化されたコードは仮想化されたまま残します。

## 検証

`NeverDUnpackTests` は識別を検査します。`NeverDUnpackExecutionTests` は、リポジトリに収めた UPX フィクスチャ（NRV2B、NRV2D、NRV2E、LZMA、および C ランタイムを使うプログラム）を Unicorn、KVM、WHP 上でアンパックし、すべてのセクションを元のファイルと比較し、復元したイメージを実行し、すべてのバックエンドが同一のバイト列を生成することを要求します。`UnpackGeneratedTests.cpp` は、テストの中で x86-64 と ARM64 向けにプログラムをパックし、そのまま離れるローダー、先にプログラムを呼び出すローダー、2 段階のローダーを、リンクされたファイルと照合して検査します。`NeverDUnpackPublicTests` は C ABI と CLI を対象とします。UPX フィクスチャは `unittests/unpack/fixtures/Makefile` で再生成できます。

# パックされた実行ファイルのアンパック

`neverd unpack` は、パックされた実行ファイルが自身のアドレス空間内に再構築するプログラムを復元します。入力を有界なゲストプロセスとして実行し、スタブが自ら生成したコードへ制御を渡す箇所を観測して、その時点のイメージを同じコンテナ形式の新しいファイルとして書き出します。仮想化の解除は行いません。保護ツールが仮想化した関数は仮想化されたままです。ビルドには `NEVERD_ENABLE_CPU_EMULATION=ON` が必要です。

## 対応する入力

コンテナ形式はファイルの検証と再構築の方法を、命令セットは転送の判定方法を決め、両者がゲストプロセスのプロファイルを決めます。この表にない入力は、何も実行される前に名前を挙げて拒否されます。

| コンテナ (`format`) | 命令セット | ゲストプロファイル | エントリの根拠 |
| --- | --- | --- | --- |
| PE32+ (`pe64`) | x86-64 | [`windows-pe64-v1`](process-emulation.md) | 実行時の観測 |
| PE32+ (`pe64`) | ARM64 | [`windows-pe64-v1`](process-emulation.md) | 実行時の観測 |

PE32+ DLL 入力は `IMAGE_FILE_DLL` で識別します。モデル化されたゲスト EXE が `LoadLibraryA`、`FreeLibrary` を呼び出し、通常の依存関係、TLS、`DllMain` のライフサイクルを使います。DLL の既定入口はプロセスアタッチ呼び出しです。任意のエクスポートの引数は推測しません。名前、序数、別名、データ、転送エクスポートを保持し、自身のエクスポートへのポインターは自己インポートに変換しません。ヘルパーが返すアドレスにも同じ規則を適用します。内部アドレスが返された場合、その位置で以前に得たインポート修復の証拠を撤回します。

## 使い方

```bash
neverd unpack packed.exe -o unpacked.exe
neverd unpack packed.exe -o unpacked.exe \
  --options='{"backend":"unicorn","instruction_limit":400000000,"transfer":2}'
```

コマンドは JSON レポートを 1 つ出力します。終了コード 0 はイメージが書き出されたこと、3 はエントリが受理される前に有界な実行が終了したこと（`outcome` は `no_entry` で、何も書き出されません）、1 は入力・オプションの不正または準備の失敗を表します。レポートには、実際に実行された `format`、`architecture`、`profile` が記載されます。C のエントリポイントは `neverd_unpack_json`、Python では `Session.unpack` です。オプションは[プロセスオプション](process-emulation.md)に `transfer` を加えたものです。スタブがより多くの資源を必要とする項目では既定値が異なります。100000000 命令、600 秒、512 MiB で、`windows.defer_unmodeled` は有効です。

## エントリの確定方法

世代ゼロはゲストローダーが入力をマップした時点のイメージです。転送は新しいコードの実行開始です。`transfers` は RVA、`generation`、スタック一致（`stack_balanced`）、入力の入口呼び出しへの帰属（`program_invocation`）を記録します。DLL ではプロセスアタッチを指します。その呼び出し前は最初の初期化処理のスタックを基準にします。

1. 既定の入口には `stack_balanced` と `program_invocation` の両方が必要です。スタブが入力入口呼び出しのスタックを返したことを示し、`entry_source` は `transfer` です。
2. OS 所有の TLS コールバック、依存 DLL の入口、デタッチ呼び出しは、スタックが一致しても既定入口にはなりません。深いゲスト呼び出しは続行します。コールバックを省略せず、スタブ署名から入口を予測しません。
3. `transfer` は初期化コールバックや段階的な転送も含め、一覧の位置で明示的に選択します。

コンパイラのスタートアップコードの形からエントリを推測することはありません。先に実行が停止した場合は、`no_entry` とプロセスの `stop_reason` が報告されます。

一度実行した 4 KiB ページも監視対象から永久には除外しません。コミット済みのゲスト RAM 書き込みは物理エイリアスを通じて訪問済みページの記録を無効化し、プロセスモデルは OS サービス後の再開前にもページを再検査します。転送の証拠は CPU デコーダーが示す実際の命令範囲だけを比較するため、隣接データの変更だけでは入口になりません。新旧コードの混在や再書き込み、同一ページの古いスタブへ戻るコールバックも監視を維持します。

## 再構築されたイメージ

セクションは RVA、観測したメモリ（実行済み初期化の効果を含む）とページ権限を保持します。追加の `.neverd` セクションにインポートディレクトリと、エクスポート呼び出しとアドレス読み込みの修復用の新しい IAT セルを置き、元のゼロ領域を保ちます。`imports` の `origin` は入力から束縛された `static` と、ゲストが書いた、または修復で追加した `runtime` を区別します。生成内容の再配置は観測していないため、観測ベースに固定し、再配置ディレクトリを削除して `IMAGE_FILE_RELOCS_STRIPPED` を設定します。

デバッグデータのファイルオフセットを書き換えるには、デバッグディレクトリと保持する各データ領域の全体がファイル内に存在する必要があります。

書き込み可能なインポートセルにはネイティブ IAT の保護範囲は不要ですが、各セルは引き続きインポート記述子によってバインドされます。読み取り専用セルには、読み取り専用かつ実行不可のセクションからなる連続した範囲が必要です。書き込み可能または実行可能なセクションをまたぐ範囲は、メモリ保護を変更せず明示的に失敗します。

既存の実行時 IAT 候補には、同じ提供モジュールの連続したエクスポートポインター配列と、元のセクション内の完全なゼロ終端が必要です。隣の提供モジュールの終端は使用できません。

ローダーの割り当て識別情報と一致する元の TLS ディレクトリでは、コールバック配列が存在しない場合や空の場合も認めます。走査で見つけた代替レコードには、完全なゼロ終端コールバック表と実際のコールバック実行の証拠が引き続き必要です。候補が複数なら明示的に失敗します。プロテクター固有の名前やバイト列は使いません。ディレクトリ選択では、生成されたコールバックの実行証拠を、完了したローダー初期化処理より優先します。 プログラムが完了済みのローダー初期化コールバックを再度呼び出しても、そのコールバックが書き換えられている場合を含め、補助的な証拠として扱います。

`materialized_tls_callbacks` はキャプチャ前に正常に戻った入力イメージの TLS プロセスアタッチコールバックを数えます。完了には OS の呼び出し記録、または引数 `(image_base, 1, 0)` による生成コードへの入口と、その ABI 戻り先および戻りスタックポインターの復元を観測した証拠が必要です。メモリへの効果は既にスナップショットに含まれます。新しい `.neverd` セクションのアダプターは、その重複するプロセス接続呼び出しだけを省き、他の通知では元のコールバックへ末尾呼び出しします。ディレクトリ、コールバック表、アダプターには新しい領域を使い、元のバイト列を保ちます。アダプターがある場合は実行可能で、新しい IAT セルが必要な場合だけ書き込み可能です。完了証拠のないゲスト内部のコールバックは変更しません。プロセス接続時、取得済みのメインスレッド TLS がテンプレートと異なる場合は、完了したコールバックがゼロでもアダプターがそのデータを独立して復元します。実行中の TLS の証拠が欠けるかサイズが合わない場合は明示的に失敗します。元のテンプレートは後続スレッド用に保ち、他の通知では取得済みブロックを復元しません。

遅延ロードでは、先行する初期化処理がコードを生成するゼロ埋めメモリを、実行可能なコールバックや入口の対象にできます。コールバック配列と TLS 割り当てメタデータには検証済みのファイル内容が必要で、通常の厳格ロードはファイル裏付け検査を維持します。OS モデルは呼び出しの帰属を示し、呼び出しの準備時や中断した呼び出し元の復元時に観察器へ通知します。これらの境界で転送監視を再設定し、コールバックと生成された入口が同じページにある場合も扱います。

`import_repair` は入口取得後の追加の有限実行 2 回を扱います。まずエクスポート呼び出しを発見し、次に補助ルーチンの状態を観測します。各回に独立したプロセス上限を適用します。命令数とイベント数は飽和加算し、`stop_reason` と診断は最後の実行、呼び出し数は発見段階だけを示します。継続アドレスがなければ状態観測を省略します。エクスポートの同一性が競合する箇所は変更しません。対象は到達経路だけで、`unpacked` は全インポートや実行成功を保証しません。

インポートのバインド順序によってエクスポートアドレスは変わり得ます。修復は証明時の識別情報を保持し、エントリ後に解決されるエクスポートも監視します。別の実行のアドレスは書き換えの根拠になりません。

発見段階はモデル化呼び出しログだけでなく、停止を起こす未モデル化エクスポートを含むディスパッチを観測します。ABI 戻り位置が読めなければ補助ルーチンの証拠に使えません。不透明エクスポートへの純粋な呼び出しを復元しても、未対応サービスによる明示的停止を維持します。

実際のエクスポート呼び出しの継続位置より前の 256 バイトから最大 256 個の開始候補を観測します。GPR PUSH/POP を前置できる `CALL rel32` は観測境界だけを示し、CALL 後のバイトを署名には使いません。6～8 バイトの呼び出し領域を `call [rip+IAT]` に変えるには、API 入口で戻りアドレスが 1 個だけ積まれ、他のレジスタ（フラグと SIMD を含む）、マッピング、永続 RAM が不変で、途中に OS 呼び出しがないことが必要です。先頭の NOP で API の正確な戻りアドレスを維持します。7～8 バイトの領域が単一 GPR に既知のエクスポートを返し、スタックと同じ保存条件を満たせば `mov r64, [rip+IAT]` にできます。結果レジスタは状態比較で決め、RSP 以外の全 GPR（R8-R15 を含む）を認めます。8 バイト領域には末尾 NOP を残します。除外するのは呼び出し元 SP より下の一時領域だけで、呼び出し元スタックは比較します。後の副作用、未解決、未完了の呼び出しは先の証拠を無効にします。実行開始位置の証拠が必要で、直前バイトを REX とみなしたり、戻り位置を共有する重複開始を認めたりしません。`observed_loads` と `repaired_loads` はアドレス読み込みを別に数えます。

`ImportObserver` は途中の実行停止でも外側のスナップショットを一つ保持します。内側の候補には独立したスナップショットがないため、その候補の以前の証拠を取り消します。外側の呼び出しにもレジスタ、マッピング、永続メモリ、OS 呼び出しの完全な比較が必要です。再帰、中断、未完了の呼び出しは証拠を取り消します。`ProcessImportsTests.cpp` と独立してリンクした DLL フィクスチャがこれらの境界を検証します。 内側の停止をまたいでスナップショットを保持するのは、観測済みのエクスポート継続位置を持つ候補だけです。

元のセクションテーブル、インポートディレクトリの配置、再配置テーブルは再構築されません。パッカーはそれらをメモリ上に復元しないためです。

## 識別

互換フィールド `packer.kind` と `packer.evidence` は `unidentified` と空配列を返します。プロテクター登録、圧縮ヘッダー解析、スタブ署名は削除しました。従来の識別 API はコンテナだけを検証します。

## 制限

検査付き実行は命令単位です。x64 Unicorn/KVM/WHP は時間とイベントで制限する `direct-user-x64-v1` に対応し、命令数を計測しません。世代の混在と繰り返しの書き込みでは追加のプロセッサステップが必要になる場合があります。復元対象は入力イメージで到達した経路であり、その外部に生成されたコードを入口にはしません。入口前の初期化が作る外部状態は移植できない場合があり、TLS コールバックの再実行にも副作用があります。未モデル化 API は明示的に停止します。修復は検証済みの 6～8 バイト x64 呼び出し領域と 7～8 バイトアドレス読み込みを扱い、他形式と未到達経路は未解決です。仮想化コードはそのままです。

## 検証

`NeverDUnpackTests` はコンテナ、安全な IAT 割り当て、競合と TLS 拒否を検証します。`NeverDUnpackExecutionTests` は Unicorn/KVM/WHP の共通経路で UPX NRV2B/NRV2D/NRV2E/LZMA と CRT を検証し、独立にリンクしたプログラム自身の初期化後のセクションと比較して、利用可能なバックエンドの出力一致を要求します。`UnpackGeneratedTests.cpp` は x86-64/ARM64 の独立プログラムを生成し、転送、段階的ロード、インポート修復、x64 Unicorn/KVM/WHP 直接実行を検証します。ネイティブ CI の必須ケースはスキップできません。`NeverDUnpackPublicTests` は C ABI と CLI を検証します。`unittests/unpack/fixtures/Makefile` で UPX 検体を再生成できます。


`UnpackLibraryTests.cpp` は独立した x64/ARM64 DLL をテスト内でパックし、依存順序、通常・生成 TLS コールバック、アタッチ失敗の後処理、入力とホストの識別、自身のファイルアクセス、名前・序数・データ・転送エクスポート、自己インポートの不在を確認します。ネイティブ Windows は別 EXE で元の DLL と再構築 DLL をロードし、宣言済みエクスポートを呼びます。検査付き・直接 WHP ケースは必須です。`CompletedGeneratedTLSCallsRequireTheAttachABI` は入口・引数の変更を拒否し、`GeneratedCallsNeedTheirReturnedStackAtTheContinuation` は誤った戻りスタックを拒否します。対象はアンパックであり、仮想化解除ではありません。

`ExportObserver` は常駐ゲスト依存モジュールの実行可能エクスポートも監視します。モデル化プロバイダーはサービス分配で観測し、入力自身のエクスポートは除外します。モジュール変更で監視を更新し、修復には現在のエクスポート識別を必要とします。記録数は宣言済みインポート上限以内です。DLL テストはシステム API とゲスト依存関数の両ヘルパーを修復し、ネイティブロードでエミュレートされたアドレスが残らないことを検証します。


`WrappedEntriesRequireExplicitTransferEvidence` は DLL ラッパーが深いスタックで復元入口を呼ぶ場合を扱います。既定は `no_entry` のままです。観測済み呼び出しを `transfer` で選ぶとロード可能な DLL を再構築できます。深い呼び出しだけでは入口と初期化処理を区別できません。
